# Rules are one-per-file markdown with YAML frontmatter, strict at sync, loud at event time

A Rule is a single markdown file, `<rule-name>.md`, in the harness-neutral `.handrail/` directory: the matcher lives in YAML frontmatter and the message is the markdown body. The message is the product (multi-paragraph prose aimed at an agent), so it stays first-class prose instead of an escaped YAML scalar. Identity is the filename; there is no `name:` field. The matcher addresses the event model explicitly (`event:` from the six-event core of ADR 0002, optional `kind:` tool kind), conditions are an implicit-AND list whose entries may be one-level `any:` groups, and each condition names one canonical payload field with the operator as the key: `matches`, `contains`, `equals`, `starts_with`, `ends_with`, `glob`, each negatable via a uniform `not_` prefix. Regex is RE2 (the engine is Go, so no lookarounds or backreferences), case-sensitive by default with inline `(?i)` opt-in; `glob` supports `**`. Actions are `warn` (the default) and `block`; `enabled:` defaults to true; there is no templating, no `raw.` passthrough field access, no `pattern:` shorthand, and no format `version:` field. Parsing is strict at sync time (any invalid rule fails the sync with errors) and loud-fail-open at event time (an unparseable rule is skipped and the failure is injected into the agent's context, naming the rule). Upstream hookify's silent fail-open, where a broken guardrail quietly stops guarding, is the failure mode this stance exists to kill. When multiple rules match one event, every message is delivered labeled with its rule name, and one block makes the outcome block. Events are ADR 0023's eight; `ask` joins per ADR 0021.

A rule may carry Examples in its frontmatter: calls, written as canonical fields, that its matcher must or must not select. An Example tests its own rule alone and never an Outcome, because an Outcome depends on tiers, Trust and enforcement state, and a proof that passes in one repository and fails in the next proves nothing about the file. Examples live in the rule file because Shadowing replaces a file wholesale, and a shadowing rule must bring its own proof rather than inherit one written for a different matcher. They run at `check`, `sync`, `doctor` and `SessionStart`, so a binary upgrade that changes what a rule matches is reported on the next session. A failing Example never changes enforcement, and nothing reads an Example as evidence that a rule works, so under ADR 0012's threat model a hostile Example can make noise and can never weaken a guard.

An enabled shadow is also tested against the `match:` Examples of the rule it replaces. A copy narrowed by one exception no longer blocks what its original is known to block once the original changes, and this is the only point where that drift is visible. Reported like any Example failure; enforcement is unchanged. A disabled stub is exempt.

## Considered options

Pure YAML with many rules per file and TOML were rejected: both demote the message to an escaped string and lose per-file toggling and clean diffs. `ask` as a third action was rejected for v1: only Claude Code supports it natively, so degradation would make it unpredictable exactly where a user wanted a human gate. Superseded for `ask` by ADR 0021, which answers the unpredictability by degrading `ask` up to `block` rather than down. Sugar aliases (`on: shell`), a one-line `pattern:` shorthand, message templating, and `raw.` field access were rejected as second vocabularies or portability traps; each can be added compatibly if a real need appears. `.claude/handrail/` as the rules home was rejected because the canonical store of a cross-harness tool cannot live inside one harness's vendor directory. Fixtures in a sibling file (Semgrep, OPA, Kyverno) were rejected over Shadowing. Asserting the effective ruleset's Outcome (cc-safety-net's `expect: blocked`) was rejected as dependent on where it runs. Disabling a rule whose Example fails was rejected as handrail inventing an allow.
