# Tests run against the compiled binary, and unit tests exist only for what a process boundary cannot produce

handrail's product is a process a harness spawns: it reads argv and stdin, writes stdout and stderr, and exits with a code the harness reads. So that is the seam the tests use. `testdata/script/*.txtar` drives the real binary through testscript, in a sandbox where `HOME` and every XDG variable point into the script's own work directory, and `testscript.Main` runs `main` itself rather than a closure around `run`, so the entry point is covered by every script. A test written at this seam asserts the thing a user gets: the exact message, the exact exit code, the file that did or did not appear.

Tests under `internal/` are the exception, and the whole list is three files: `main_unit_test.go` for a stdout that fails every write, `internal/harness/harness_test.go` for an adapter no table lists and for two unexported helpers, `internal/rule/trust_test.go` for a path carrying a newline. Each is there because no invocation of the binary can produce the input: testscript always hands the command a real file for stdout, `Adapters()` is a fixed list, and argv cannot carry a newline everywhere the tests run. Anything reachable through the CLI is tested through the CLI, even when a white-box test would be shorter, because a second weaker seam asserting the same behaviour is a second thing to keep true.

CI fails under 95% statement coverage while the real number is higher, currently 97.7% on darwin. The gap is deliberate. What is left uncovered is failure paths belonging to the operating system rather than to handrail: a write to a file descriptor that has just been opened successfully, `json.Marshal` over values that are marshalable by construction, `filepath.WalkDir` returning an error its own callback never produces, and `os.Getwd` failing, which needs a deleted working directory and therefore happens on Linux but not on darwin, where the answer comes from the vnode name cache. A gate set at the measured number would fail whenever a platform disagreed about one of those, which is a build break that teaches nothing.

## Considered options

Unit tests as the primary seam, with testscript reserved for a few smoke tests, was rejected: most of what this tool gets wrong is in the seams between parsing, discovery, and the filesystem, and a unit test mocks exactly those away. A 100% gate was rejected for the reason above: reaching it means either testing the standard library's error returns through injection scaffolding, or writing platform-specific tests that pass by being skipped. Injecting a filesystem interface to reach the remaining paths was rejected on the same grounds as the runtime dependency rule: an abstraction whose only caller is a test is code the guardrail itself does not need. Guarding an `os.Getwd`-failure table with `runtime.GOOS == "linux"` was considered and skipped: it is dead weight on the machine the code is written on, and coverage clears the gate by nearly three points without it.
