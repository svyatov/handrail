# One harness event, one payload per edit

A harness event may describe more than one edit. A Codex `apply_patch` envelope is the first case and will not be the last: OpenCode and Cline ship the same envelope, Gemini and Cline both have multi-target reads, and Amp's own plugin API types a tool call's modified files as a list. handrail therefore normalizes one event into one or more canonical payloads, one per edit, and evaluates every one of them, taking the strongest Outcome. Per edit: `path`, `content`, `removed_content`, `writes_empty`, `deletes` and `unreadable`. Per call, copied into every payload: `event`, `tool`, `prompt` and the working directory. A payload's kind is not per call: it is the act that payload describes.

Two signals land with the change. `deletes` reports that a call removes a file, which absence would otherwise render identical to a truncating write and which ADR 0010's `writes_empty` deliberately does not cover, since a deletion is not a positively read empty value. `unreadable`, from ADR 0012, becomes per-edit: a file section handrail cannot read marks its own payload and leaves the others evaluated, while an envelope with no recognizable header marks the single payload it yields. No file-editing tool that touches one file per call can ever set `deletes`, so a `deletes` rule covers the harnesses whose edit tool is the V4A envelope and nothing else; on Claude Code the equivalent act is `rm` under `kind: shell`.

A rename is one payload whose `path` holds both the source and the destination, since `*** Move to:` sits inside one `*** Update File:` section. The two paths are two Candidates (ADR 0024), so a `not_` term on `path` fires when either path fails it.

A shell call is split the same way. Beside its `shell` payload it yields one payload per file its syntax names: `file_edit` for a write, `file_read` for a read, each with that one `path` and the per-call fields, and none of `command`, `content`, `deletes`, `writes_empty` or `removed_content`. The files are those of redirects and of a fixed list of programs with fixed argument grammars, taken from Claude Code 2.1.280's own permission table, so handrail's reach over shell is the reach Claude Code's own `Edit` and `Read` deny rules already have, now on both harnesses. A program joins only if a fixed grammar over its own arguments names the file it writes or reads. A target handrail cannot read literally sets `unreadable: path`, and an unknown flag on a listed program makes every operand its own payload with `unreadable: path`, `file_edit` if the program can write and `file_read` if it only reads.

The list can never be complete, since any program writes files, so this is a denylist aid: a `not_` `path` rule is never an allowlist over shell, and a guard that must hold against a hostile agent keeps a `command` rule beside its `path` rule. `cd` is not followed and relative targets stay as written.

On Codex, the shell form of `apply_patch` reaches hooks as `Bash` and is applied as a patch after them, so the Codex Adapter reads it as the patch it is, with the per-edit payloads above.

Rules now block calls they previously allowed, because the files they always claimed to cover have become visible, and `kind: file_edit` and `kind: file_read` rules now reach shell calls. This ships as a MAJOR. A static warning at `check` time is not possible, since whether a given rule's reach widens depends on calls that do not exist yet.

## Considered options

Making `path` and `content` multi-valued, reusing the mechanism ADR 0011 introduced for `command`, was rejected. Multi-valued fields are safe for `command` because every value is a reading of the same program, so a condition that matches any of them is answering about one thing. Values drawn from different files are not one thing, and a rule conditioning on both `path` and `content` would match across the seam: the `.env` in file one and the secret in file two, blocking a call the user never asked to block. The defect is correlation between fields rather than quantity within one, so no quantifier fixes it. Keeping the existing first-file-only shortcut was rejected because on Codex every file edit is an `apply_patch`, so it is not an edge: a two-file patch hid the second file from every `path` and `content` rule with no notice. That is the silent under-blocking ADR 0012 closed elsewhere. For shell calls: redirects only was rejected because it misses `rm` of a guard file and every `cp`; writes only with kind-less path rules was rejected because it makes every write guard fire on the `Read` tool; `path` Candidates on the `shell` payload were rejected because a `kind: file_edit` rule never reaches them; a multi-valued `kind` on one payload was rejected because it lets a read rule fire on a write, since the kind and the path come from different acts; and shell file payloads carrying `content` and `deletes` were rejected as splitting more than any rule needs.
