# A rule names a tool in the harness's vocabulary and a category in handrail's

handrail carries two tool vocabularies, and each has exactly one job. `tool` is the harness's own: the name on the wire, plus every alias that harness documents, including names the tool has been renamed away from. `kind` is handrail's: a small classification an Adapter assigns, which is what makes a rule reach both harnesses. A rule that names `WebFetch` is scoped to the harness that calls it that, and says so. A rule that says `kind: network` reaches both.

The alternative was one vocabulary doing both jobs. A handrail-invented canonical tool name would port perfectly and would make handrail the owner of a name map for every tool on every harness, restated at every release, going stale between them, with a tool released after the binary unnameable until a new one ships. It would also duplicate `kind` with a worse spelling: `Bash` as a Gemini alias for `run_shell_command` says nothing `kind: shell` does not already say. So the Adapter relays names its harness publishes and never mints one.

Naming is where this stops. A named tool can be selected wholesale, which is what makes an unguardable tool guardable, but the fields a tool carries are a separate question per field, because they do not generalize: the three harnesses surveyed took the subagent task text under three different keys, and their fetch tools disagreed on whether a URL is a field at all. `raw.*` conditions would answer all of that at once by addressing the harness payload directly, and are refused: a new addressing grammar, harness-specific by construction, which is the inverse of the property the two-vocabulary split exists to protect. `raw.*` reopens when a rule exists that no canonical field can express.

A kind lands on a stated test rather than on judgement: classifying a tool into it is not a judgement call, and one harness carries the concept while the other does not carry it in a different shape, the same test a field meets (below). A harness with no such tool has a hole, which the capability matrix states. `agent` clears it on both harnesses. `network` clears it: Claude Code's `WebFetch` and `WebSearch` fire hooks, and so does Codex's `webrun`, while Codex's hosted `web_search` never reaches a hook, which the capability matrix records. `search` and `notebook` are not added: a `search` kind with no field to narrow it could only block all searching, and `NotebookEdit` is already `file_edit`. Neither is reclassified, because moving a tool into an existing kind makes rules written for that kind start firing on calls they never named.

A field lands when one harness carries the concept and the other does not carry the same concept in a different shape. A harness with no such call has a hole, which the capability matrix states. A harness carrying the concept in another shape is a disagreement, reconciled in its Adapter before the field lands. This replaced the two-of-three survey bar when support narrowed to Claude Code and Codex, and `url` was its first application. Per-tool fields graduate one at a time, each against this test.

Key presence applies within a field's stated source; spec section 1 lists each field's source. `prompt` reads the event envelope on `UserPromptSubmit`, where there is no tool input at all, so a tool input key spelled `prompt` is never a candidate for `prompt` and reaches `agent_prompt` instead. This is a clarification of key presence rather than an exception to it, because an exception to key presence is how a field that validates and silently never fills comes back.

A generic type key has a cost, recorded for when one appears. Were a harness's key a generic word that means another thing on another tool (`mode`, `source`, `agent`), it would map only on the tools the Adapter knows by name, and lose coverage of an unrecognised tool on that harness alone.

Six per-tool fields have graduated under this test, in this order: `agent_type` and `agent_prompt`, `url` and `domain`, `model`, `removed_content`, `response`, and `network_grant` and `unsandboxed`. Spec section 1 defines each and names its source. What follows is only the reasoning that section does not carry.

`agent_type` and `agent_prompt` are read by key presence and not gated on `kind: agent`, because gating on kind would let a rule parse, pass `check` and silently never fire on a spawn tool the Adapter has not heard of. `agent_prompt` does not reuse `prompt`: Claude keys the task text `prompt`, and a rule written against what the human typed would start firing on what the agent told a subagent, which is the opposite trust level. The type is the field that carries the risk: no harness puts a permission override on the spawn payload, so the type string is the only thing on the wire that names the definition file which can widen a subagent past its parent.

`domain` is strict because of parser differential: Claude fetches through Node's WHATWG parser, which maps `example。com` to `example.com` and reads `\` as `/`, and Go's `net/url` does neither. Refusing every host with a character outside `[a-z0-9.-]` refuses every case the two could disagree on with the standard library alone. `golang.org/x/net/idna` was declined: a dependency whose mapping would have to track Node's exactly.

`model` reads unscoped although a generic key would need scoping, because a generic key is one that means another thing on another tool, and `model` names a model on whatever tool carries it, as `path` and `content` do. It is never normalized: nothing on the wire can be steered, and the steering that exists happens off the wire, in a definition file, a Codex role file or an environment variable.

`removed_content` needs no disk read, which is why ADR 0010's refusal to resolve edits does not reach it. `unreadable` was refused for the calls that name no removed text, because it would mark every whole-file write. Names refused: `removed` reads as a boolean beside `deletes` and `writes_empty`; `old_string` is one harness's key; `old_content` suggests the file's previous state, which ADR 0010 refused as a meaning for `content`.

`response` is text the agent writes, so under the adversarial threat model a rule on it is a nudge rather than a gate, which the bound on the Action makes acceptable: a block on `Stop` continues the agent once. Names refused: `last_assistant_message` is long and uses one harness's word; `message` is already the rule's Message. The transcript was refused as a second field: it costs disk I/O on a format Claude Code calls internal, and the agent can write into it. It reopens when a harness documents a stable transcript format.

`network_grant` and `unsandboxed` come from Claude Code only, with Codex a hole under the landing test, since its escalation request never reaches a hook. They are also the first generic key: `allowed_domains` means a grant on three tools and a result filter on `WebSearch`. That is answered by scoping the read to named tools in the Adapter, as `ws.url` is, and not by a per-key scoping mechanism, because one key does not earn one.

## Considered options

A handrail-canonical tool taxonomy was rejected above. Carrying only raw wire names with no aliases at all was rejected because it makes every Codex `apply_patch` rule and every renamed tool the user's problem to spell twice, for a saving of two table entries. Reporting a rule that names a tool the running harness never emits was rejected because handrail cannot enumerate a harness's tools and therefore cannot tell a typo from a tool it has not heard of; a warning it cannot be sure about trains people to ignore the channel, which is the argument that already refused an unsilenceable `check` warning and a banner on every `warn`. The first kind test, at least two of the modelled harnesses shipping such a tool whose hooks fire, was replaced when support narrowed to Claude Code and Codex, by the same test a field meets.
