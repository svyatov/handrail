# An empty field is absent, and the one fact that hides gets a field of its own

`Payload.SetField` refuses every empty value, so a field the call carries empty is absent and no condition matches it in either polarity. This holds for every canonical field, with no exceptions: an empty value is no answer about a field rather than an answer of nothing. `content` is where that costs something, because a `Write` carrying `content: ""` leaves a real file with nothing in it, and an `Edit` carrying `new_string: ""` removes text and writes none, and no content condition sees either. Presenting the empty string instead would fire every `not_contains` rule against text nobody wrote, blocking calls the rule never meant, which is the louder failure. So the trade is kept and the gap is closed from the other side: a `file_edit` call carrying a `path` whose written text was positively read as the empty string also carries `writes_empty: true`, meaning the call writes no text, and a rule addresses the act directly. On a whole-file write the file is left empty; on an edit, text is removed and nothing is added, which is how a rule on `removed_content` sees a pure removal. Claude Code's `Edit` with an empty `old_string` and an empty `new_string` creates an empty file, so it counts. The signal is derived from the call alone. Handrail does not stat or read the target, so it does not distinguish truncating a full file from creating an empty one, and it never fires for a key the call omitted, a key holding a non-string, or a patch envelope handrail could not parse: a guardrail that cannot read a call must not report a finding about it, which keeps this from becoming a fail-open dressed as a match.

The same rule applied a second time: what handrail could not read is declared through its own field, `unreadable` (ADR 0012), while the field that failed stays absent. So the fact absence would otherwise hide gets a field of its own, and it did so twice.

The same place cleans every `path` lexically, as Go's `path.Clean` does, and never joins it to cwd, so an Example and `test --field` are cleaned the same way the hook path is. A raw path defeats both polarities: `src/../.env` satisfies a `not_glob: **/src/**` allowlist, and `secrets/./key` escapes a `**/secrets/*` denylist, since `*` never crosses `/`. A path that sets `unreadable: path` stays as written, because an expansion in it may hold a `/` and cleaning around it would drop the text a denylist matches. A `glob` or `equals` term on `path`, in either polarity, whose value cleaning would change can never be met, so it is a validation error. Before v2 such a rule matched a shell path as written, and without the error it would stop firing after the upgrade with no notice. Symlinks are a named limit: handrail never reads disk, and a symlink already escapes every `path` rule, so lexical cleaning adds no hole.

## Considered options

Presenting the empty string as a value was rejected for the reason the trade exists: it turns every `not_contains` rule into a false positive against text nobody wrote. A general `empty:` operator applying to any field was rejected as a facility for a problem with one instance, and because its polarity is circular, the absent-field rule cannot govern the one operator whose subject is absence. A marker field listing every empty arrival was rejected for its encoding: a comma-joined list matched with `contains` collides on substrings. Excluding an `Edit` with an empty `old_string` and an empty `new_string` as a no-op was dropped: in Claude Code an empty `old_string` means create, so the call is an empty create. Resolving the edit against disk before evaluating, so `content` means the file as it will be, is rejected. Budget is not the reason: at a measured 4.87 ms median for a whole hook invocation the read fits the 20 ms budget (spec section 10) with room, and no surveyed harness makes the read necessary, since all nine edit tools across seven harnesses carry the written text in the payload. Meaning is the reason. Resolved content answers for text nobody in this call wrote, so a rule against a hardcoded secret would fire on every edit to a file that already holds one, including the edit that removes it. That is the same false positive against text handrail supplied, arriving from the other side of the same trade. It is also the only canonical field that would describe a state the call did not create: `command` is what the call runs, `path` is what it touches, `deletes` and `writes_empty` are what it does. handrail guards acts, and a guarantee about what a file holds belongs to something that reads files. No payload fact reopens this. A harness whose edit tool omits the written text leaves `content` absent and sets `unreadable`, which is a marker rather than a reason to read disk. Only a decision to guard file states as well as acts would reopen it, and that is a new question rather than this one returning. Adding `stat` to distinguish a truncated file from a new empty one was rejected as precision the guardrail cannot trust, being stale by the time the call runs. Keeping the raw path as a second Spelling beside the cleaned one was rejected: a `not_` term fires only when no Spelling matches, so the raw spelling keeps the allowlist bypass open. Setting `unreadable: path` on a `..` segment was rejected: it trips every fail-closed rule on `cat ../README.md` and leaves `.` and empty segments open.
