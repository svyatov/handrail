# The CLI ships nine commands; the plugin ships two skills, one agent, and a bootstrap hook

The Go CLI's v1 surface is nine commands: `sync`, `hook`, `check`, `test`, `trust`, `advise`, `import hookify`, `doctor`, and `version`. `handrail sync` keeps the glossary's term: it validates via `check`'s logic, then detects every installed harness (`~/.claude`, `~/.codex`) and writes each one's native config, scopable with `--harness`; harness identifiers are the harness's own binary name (`claude`, `codex`). `handrail hook <harness> <event>` is the entrypoint sync installs, payload JSON on stdin, exit codes per the harness protocol; visible in help but documented as installed by sync, not for humans. `handrail check` strict-validates all tiers and prints the annotated effective ruleset (the same printout sync gives); since adding a rule needs no re-sync (ADR 0004), check is the authoring-time validation surface. `handrail test <event> [--kind] [--field key=value]... [--stdin]` is the minimal dry-run: matched rules with tier and action, then the final outcome. `handrail advise [rule-name] [--harness]` is the Advisor's single invocation: no argument audits every rule in every tier, a rule name scopes to one (the authoring-time call). Machine-readable output is a uniform `--json` flag on `advise`, `check`, and `test`: advise emits an array of `{rule, tier, harness, mechanism, entry, location, scope_widening, caveats}` where `entry` is the exact native text to paste (ADR 0005) and `scope_widening` is null when tier and entry scope match; test emits `{outcome, matched: [{rule, tier, action, message}]}`; check emits `{rules: [{rule, tier, event, kind, action, enabled, shadowed_by, path}], errors: [{path, message}]}`. Exit codes: 0 success; 1 usage, internal, or validation error; 2 reserved for "blocked" (`test`, and `hook` per harness protocol). `doctor` is offline-only: binary location and version; per installed harness, hook entries present, current, and pointing at an executable that exists; the current repo's tier discovery, trust state, and `local/` exclusion line; and a rule validity summary.

The Claude Code plugin ships `/handrail:add` (describe a guardrail in words; the skill writes the rule file, runs `check`, relays `advise --json`), `/handrail:analyze` backed by a `conversation-analyzer` agent (flow design is its own decision), and a SessionStart bootstrap hook. Bootstrap: the plugin pins a binary version; on miss or pin mismatch, SessionStart downloads the matching GoReleaser artifact for the OS/arch from GitHub Releases, verifies sha256 against the release's `checksums.txt`, and installs to `$XDG_DATA_HOME/handrail/bin/handrail` (PATH untouched; sync writes the absolute path into hook entries); after a fresh install it runs `handrail sync` once, so the plugin works with zero manual steps; a PATH-installed binary (brew, `go install`) is respected and never overwritten. There is no CLI `analyze`: analysis needs an LLM, so the agent reads the transcript and drafts rules while the CLI contributes `check` and `test`.

## Considered Options

`init`, `add`/`new`, `list`, and `enable`/`disable` commands were rejected: first run is install plus sync with nothing to scaffold, a rule is one markdown file a human or skill writes, `check` already prints the effective ruleset, and ADR 0004's disable stub is a one-line file; any of these can be added if real friction shows. A standalone per-file `validate` was rejected because `check` already names the failing rule. Having `test --stdin` read a canonical payload was rejected once it shipped: nothing emits that shape, so the only way to get one was to hand-translate a capture, and building it needed a second normalization beside the Adapter's, free to disagree with the hook path that `test` exists to predict. `audit` as the Advisor command name was rejected as a second word for a glossary concept. `apply`/`install`/`compile` lost to `sync` for the same vocabulary reason. Long harness identifiers (`claude-code`, `codex-cli`) lost to the binary names users already type. Bundling per-platform binaries in the plugin's `bin/` was rejected: plugin bloat, undocumented exec-bit survival in the plugin cache, and a path that changes on every plugin update while hook entries need a stable one. Manual-install-only (the LSP-plugin precedent) was rejected because the primary UX would send the user out of the harness before anything works.
