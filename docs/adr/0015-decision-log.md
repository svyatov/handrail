# The decision log records handrail's own reasoning, unredacted, and only where it was asked for

A guardrail that fires and leaves no trace cannot be tuned, and afterwards nobody can say why a call was blocked. The obvious fix, and the one most of the field ships, is a log of every tool call the hook sees. handrail refuses it, because that file already exists twice: Claude Code and Codex CLI both persist every call with its arguments in full and in plaintext, on the same disk. A third copy would cost an append on every event, which is most of the performance budget, to store data handrail did not produce.

What handrail does produce, and what nothing else keeps dependably, is the decision. Claude Code stores a hook's stdout including its decision and reason, but its documentation calls the transcript format internal and subject to change on any release, and deletes the file after thirty days by default. Codex stores the command and no hook decision at all. So the log holds handrail's side and only handrail's side: the rules that matched, their tiers, the Outcome, and whatever handrail could not read. A no-match event writes nothing, which is what keeps the hot path free of I/O.

The log is off until the user grants a Project root, in the path-once registry shape Trust already uses. The cost is real and is taken deliberately: a log you must enable before the incident answers nothing after it. It is taken because the alternative is a tool that begins writing an unredacted record of a developer's commands on first run without being asked, and because the question this log answers, "why did my rule do that", is one the user is already asking at the moment they turn it on.

Nothing in the file is redacted. The line handrail writes sits beside the harness's own unredacted transcript, the shell's history, and the terminal scrollback, all owned by the same user on the same disk, so a redacted copy in the middle lowers exposure by nothing while committing the project to a corpus of provider-token patterns that has to be kept current forever. This reverses the moment the log leaves the machine: a team, CI, or upload surface would make handrail the party that moved the secret, and redaction would become its job. No such surface exists or is planned.

The Analyzer (ADR 0007) sends log content to a model provider, which is a partial case of this condition. Lines from the current session cost nothing, because those tool calls are already in the model's context. Lines from earlier sessions are a new movement, so they are bounded rather than redacted: history reaches the Analyzer as counts and rule names from `check --stats`, and a payload reaches it only through `handrail log --rule` for a rule a proposal concerns, with the number of lines pulled reported to the user. The conclusion stands because the provider is the user's own, in a session the user started.

## Considered options

A log of every event, which is what cc-safety-net, secguard and dcg all write, was rejected on both grounds above: it duplicates a file the harness already keeps, and it puts an append on a path whose whole design goal is doing no I/O when no rule matches. Redaction, cc-safety-net's twenty provider-token regexes plus assignment and PEM stripping, and secguard's Shannon-entropy detection, was rejected because it would guard the only copy of the command that is not already exposed, which is no copy at all. Logging on by default was rejected because an unrequested plaintext record of a developer's commands is a surprise a guardrail tool cannot afford, and because with matches being exceptional the file is nearly always empty anyway. An environment variable as the switch was rejected because the hook runs in the environment the harness inherited when it launched, so exporting the variable in the shell you are sitting in does nothing: a switch that silently fails at the moment you reach for it is worse than no switch. A configuration file was rejected as a whole format to specify, validate, tier and document, for one boolean, in a tool whose configuration is its rules. A per-rule `log:` frontmatter field was rejected because logging is a property of a debugging session rather than of a rule, and ADR 0003 refused a second vocabulary for less. A separate `explain` command, cc-safety-net's per-event decision trace, was rejected as a third spelling of an answer handrail already gives: `test --stdin` replays a real payload and reports the matched rules with tier, action and Outcome, so a logged line plus `test` reconstructs any trace `explain` would print. Age-based retention, Claude Code's own thirty-day answer, was rejected because their file grows on every message and this one grows on a match, so a clock sweep on the hot path would defend against a volume that cannot occur; the failure a bound exists for is a rule matching every event in a loop, which a size cap catches and an age cap does not. Per-project log files, Claude Code's slugged-path shape, were rejected for needing a slug scheme and therefore a collision answer, where one file needs neither and makes rotation a rename.
