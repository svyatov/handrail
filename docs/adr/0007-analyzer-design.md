# The Analyzer is on-demand, human-approved, and ships as a plugin skill on both v1 harnesses

Conversation-analysis-driven rule creation is performed by the Analyzer, an LLM-side agent shipped inside each harness plugin, never by the CLI (ADR 0006). It runs only on demand (`/handrail:analyze`); there is no automatic session-end analysis and no nudge hook, because hooks cannot run an LLM and a heuristic nudge cannot tell a correction-heavy session from a clean one without one. Input scope is the current session's transcript via `transcript_path`. The Analyzer receives the effective ruleset (`handrail check --json`) and proposes new rules only, skipping behaviors already covered. Each proposal is a complete rule draft (ADR 0003) with a rationale and the transcript evidence that motivated it; nothing is written without per-rule user approval. On approval the skill writes the file, validates with `handrail check`, replays the motivating event through `handrail test` to prove the rule actually matches its own incident, and relays `handrail advise --json`. The skill suggests a tier per rule: Project-personal by default, Global when the behavior is clearly project-agnostic; Project-shared stays a deliberate manual act. Delivery is a harness-native plugin on both v1 harnesses: the Claude Code plugin (ADR 0006) and a native Codex plugin, with the handrail repo serving as its own Codex marketplace (`.codex-plugin/plugin.json`); the Codex plugin has full parity (add skill, analyze skill, SessionStart bootstrap hook with the same install-on-miss logic), extending ADR 0006's plugin section, which was written as Claude-Code-only. Skills are authored once and referenced by both plugin manifests. Where a harness's capability matrix lacks transcript access, the feature is absent and the documented fallback is describing the incident in words to `/handrail:add`; Claude Code writes `transcript_path` asynchronously, so the Analyzer must tolerate a slightly stale tail. The spec names the signal categories (explicit user corrections, repeated instructions, manual reverts and interventions, near-miss dangerous actions) as a non-exhaustive definition of "worth preventing"; exact prompt wording is implementation.

## Considered Options

Automatic analysis on SessionEnd was rejected as impossible without a daemon, and a SessionEnd nudge was rejected as per-session noise. A historical-sweep scope and an explicit transcript-path argument were rejected for v1; both can be added compatibly. Proposing edits to existing rules (tuning a rule that fired but was overridden) was rejected for v1 as a different feature with a different evidence model. For Codex delivery, a manual drop-in and `npx skills` (skills.sh) as the canonical install were rejected: Codex's native plugin marketplace is first-party, supports a `hooks/` directory for the bootstrap, and keeps one symmetric story across harnesses; skills.sh remains a docs-mentioned bonus channel for non-v1 harnesses. An analyze-only Codex plugin lost to full parity on the same zero-manual-steps rationale ADR 0006 accepted for Claude Code; the one caveat is Codex's one-time trust review for non-managed plugin hooks.
