# The Analyzer is on-demand, human-approved, and ships as a plugin skill on both v1 harnesses

Conversation-analysis-driven rule creation is performed by the Analyzer, an LLM-side agent shipped inside each harness plugin, never by the CLI (ADR 0006). It runs only on demand (`/handrail:analyze`); there is no automatic session-end analysis and no nudge hook, because hooks cannot run an LLM and a heuristic nudge cannot tell a correction-heavy session from a clean one without one. Input scope is the current session's transcript, plus the Decision log (ADR 0015) where the Project root is granted: statistics for every rule from `handrail check --json --stats`, and one rule's lines from `handrail log --rule` when a proposal concerns that rule. The Analyzer proposes new rules, tunes existing ones, and concludes trials (ADR 0016). A proposal that weakens is identified by the act it performs, computed rather than self-declared: editing or deleting an existing rule file, shadowing a lower-tier rule by name, or setting `enabled: false`, `trial: true` or `agent_only: true`. It quotes its evidence verbatim and is approved alone, because under a prompt-injected agent the party proposing a retirement may be the party that produced the evidence for it. Each proposal is a complete rule draft (ADR 0003) with a rationale and the evidence that motivated it; nothing is written without per-rule user approval. On approval the skill writes the file, validates with `handrail check`, and replays the motivating event through `handrail test` to prove the rule actually matches its own incident; an amended rule must no longer match its incident; a truncated payload with no transcript copy is not replayed, and the skill says so. The skill suggests a tier per rule: Project-personal by default, Global when the behavior is clearly project-agnostic; Project-shared stays a deliberate manual act. Delivery is a harness-native plugin on both v1 harnesses: the Claude Code plugin (ADR 0006) and a native Codex plugin, with the handrail repo serving as its own Codex marketplace (`.codex-plugin/plugin.json`); the Codex plugin has full parity (add skill, analyze skill, and since ADR 0022 the survey skill, SessionStart bootstrap hook with the same install-on-miss logic), extending ADR 0006's plugin section, which was written as Claude-Code-only. Skills are authored once and referenced by both plugin manifests. Where a harness's capability matrix lacks transcript access, the feature is absent and the documented fallback is describing the incident in words to `/handrail:add`; Claude Code writes `transcript_path` asynchronously, so the Analyzer must tolerate a slightly stale tail. The spec names the signal categories (explicit user corrections, repeated instructions, manual reverts and interventions, near-miss dangerous actions) as a non-exhaustive definition of "worth preventing"; exact prompt wording is implementation.

## Considered options

Automatic analysis on SessionEnd was rejected as impossible without a daemon, and a SessionEnd nudge was rejected as per-session noise. A historical sweep of transcripts is still rejected: they are large, conversational, and one per session. The Decision log answered the need it served, because it is handrail's own, bounded, and granted per project. An explicit transcript-path argument was rejected for v1 and can be added compatibly. Proposing edits to existing rules was rejected for v1 as a different feature with a different evidence model, and the Decision log is that evidence model. Tuning stays in one skill because its strongest signal, a rule that fired and was then overridden by the user, is one fact split across the log and the transcript. Two signals the log seems to offer were rejected as evidence on their own: frequency, because the log records no non-matches and so has no rate, and a rule with no matches, because a guardrail that never fires is usually working. Reading the harness's own hook-result entries was rejected: Claude Code's are in a format its documentation calls internal and unstable, and Codex keeps none. An integrity scheme for the log was rejected: an agent that can forge the log can equally edit the rules, so the add skill teaches a rule over handrail's state directory instead (ADR 0020's answer, extended). For Codex delivery, a manual drop-in and `npx skills` (skills.sh) as the canonical install were rejected: Codex's native plugin marketplace is first-party, supports a `hooks/` directory for the bootstrap, and keeps one symmetric story across harnesses; skills.sh remains a docs-mentioned bonus channel for non-v1 harnesses. An analyze-only Codex plugin lost to full parity on the same zero-manual-steps rationale ADR 0006 accepted for Claude Code; the one caveat is Codex's one-time trust review for non-managed plugin hooks.
