# handrail v2 specification

handrail is a cross-harness guardrail manager: users declare rules once, in one neutral format, and handrail enforces them through each harness's native hooks. The engine is a performance-critical Go CLI; a thin plugin per harness is the primary UX. Harnesses: Claude Code and Codex CLI, the two the project can test. One rule reaching both is the product; the spec claims nothing about any other harness.

Rule semantics assume hostile input, because a prompt-injected agent produces every input a careless agent does and worse. The hook path is best-effort and never a security boundary: every harness has a documented way to switch hooks off (section 4), and handrail detects those it can see rather than claiming to defend them.

Vocabulary is defined in [CONTEXT.md](../CONTEXT.md); every capitalized term below (Rule, Rule tier, Adapter, Candidate, Analyzer, Surveyor, Sync, ...) means what the glossary says. Rationale lives in [docs/adr/](adr/); this spec states the outcome and links the ADR. Research evidence lives in `docs/research/` on the `research/*` branches.

## 1. Event model

ADRs: [0002](adr/0002-claude-code-event-vocabulary.md), [0023](adr/0023-event-ring-and-the-meaning-of-stop.md).

Canonical event names are Claude Code's, verbatim. An event is in the model when a rule on it has a job no other event does, on at least one harness. An event one harness lacks degrades to skip there, reported at sync. `SessionStart` fires again after a compaction on both harnesses, so a `SessionStart` rule is how standing context survives one. A `SessionStart` rule does not reach a subagent, and a `SubagentStart` rule does.

| Event | Fires |
|---|---|
| `PreToolUse` | Before a tool call. Can block or ask. |
| `PostToolUse` | After a tool call succeeds. Warn only. |
| `UserPromptSubmit` | When the user submits a prompt. |
| `SessionStart` | Session begins, resumes, or is compacted. Warn only. |
| `SessionEnd` | Session terminates. Warn only. |
| `Stop` | The agent finishes responding. A block continues it once. |
| `SubagentStart` | A subagent begins. Warn only. |
| `SubagentStop` | A subagent finishes responding. A block continues it once. |

### Canonical payload

ADRs: [0008](adr/0008-hookify-importer-mapping.md), [0010](adr/0010-payload-field-semantics.md), [0013](adr/0013-naming-a-tool.md), [0014](adr/0014-one-payload-per-edit.md).

- An in-process value the Adapter produces, not an input format. Nothing reads one from stdin: `hook` and `test` both take the harness's own payload and normalize it, so this shape has exactly one producer and no wire spelling to keep in step.
- One harness event yields one or more payloads: one per edit a patch makes (section 2, "Several edits in one call"), and for a shell call one per file its syntax names beside its `shell` payload (below). Every payload is evaluated, and the Outcome is the strongest across all of them.
- Every payload carries `event`, `harness`, `session_id` and `cwd`; a tool event's payload also carries its own `tool_kind`, except one handrail could not parse (section 2, `unreadable`). These are not condition fields: `event:` and `kind:` select on `event` and `tool_kind`, and nothing addresses `harness`, `session_id` or `cwd`. A condition names one of the fields listed below, a closed set, and any other name is a validation error.
- `tool_kind`, spelled `kind` in rules, `test --kind` and the Decision log, assigned by the Adapter per payload: `shell`, `file_edit`, `file_read`, `mcp`, `agent`, `network`, `other`. A kind describes what one payload does, so a shell call's file payloads carry `file_edit` or `file_read`. A tool that is two things at once takes the kind whose fields a rule can read: Claude Code's `Monitor` is `shell`. There is no `search` kind: with no search field it could only block all searching, and moving search tools into an existing kind would make rules written for that kind start firing on calls they never named. `other` is every call classified as nothing, a set that shrinks as kinds are added.
- **Fields and kinds land on one test.** A field or kind lands when one harness carries the concept and the other does not carry the same concept in a different shape; a kind must also classify without a judgement call. A harness with no such call has a hole, which the capability matrix states. A harness that carries the concept in another shape is a disagreement, reconciled in its Adapter before the field lands.
- Per-kind normalized fields: `command` (shell); `path` and `content` (file_edit); `path` (file_read); `server` (mcp); `prompt` (UserPromptSubmit). `content` is the text the call writes, never the file as it will be after the write (added by ADR [0008](adr/0008-hookify-importer-mapping.md), scoped by ADR [0010](adr/0010-payload-field-semantics.md)). Two file_edit signals report facts an absent field would otherwise hide: `writes_empty` when the call writes no text, and `deletes` when the call removes the file. `removed_content` is the text an edit names as removed. A field is read by key presence rather than by kind: a tool handrail does not classify still contributes its `command` if the call carries one, so a tool name a harness adds after a release is read rather than dropped. Its kind stays `other`, so a `kind: shell` rule does not reach it and a kind-less `command` rule does. That `command` is parsed as every `command` is (section 2), but only a `kind: shell` call yields file payloads. Every `path` is cleaned lexically, as Go's `path.Clean` does, and never joined to cwd: `.` and empty segments go, a `..` removes the segment before it, and only a leading `..` on a relative path survives, so `src/../.env` is `.env` and `secrets/./key` is `secrets/key`. A path that sets `unreadable: path` stays as written, since an expansion in it may hold a `/`. Cleaning happens where a field is set, so an Example's `path` and `test --field path=` are cleaned the same way. Claude Code's file tools send absolute paths and Codex's patch headers relative ones, so a path glob starts with `**/`.
- Every canonical field reads from one stated source, and key presence applies within it. The tool input: `command`, `path`, `content`, `removed_content`, `agent_type`, `agent_prompt`, `model`, `url`. `path` reads `file_path`, else `notebook_path`; `content` reads `content`, else `new_string`, else `new_source`; a key spelled `path` (Grep, Glob) is not a source, so it never fills `path`. On an `apply_patch` file section, `content` is its `+` lines joined with newlines, without the `+` and without context lines, across all of the section's hunks. Codex's `apply_patch` carries its envelope in `tool_input.command`, which fills no `command` (section 2, Several edits). The tool name: `tool`, and `server` on an MCP call. Adapter knowledge of named tools: `network_grant`, `unsandboxed`, and the nested `url` of `Monitor` and `webrun`. The event envelope: `prompt` on `UserPromptSubmit`, `response` on `Stop` and `SubagentStop`, `agent_type` on `SubagentStart` and `SubagentStop`. Derived from the call: `writes_empty`, `deletes`, `domain`, `unreadable`. So a tool input key spelled `prompt` is never a candidate for `prompt` and reaches `agent_prompt` instead, and the `model` key Codex puts on every hook envelope, the session's current model, is never a candidate for `model`.
- `tool` names the tool called, and is carried for every kind. It holds every name the harness itself answers to for that call: the name on the wire, plus any alias the harness documents, including a name the tool used to have. Codex reports `apply_patch` and matches it as `apply_patch`, `Edit`, or `Write`, so all three are Spellings; Claude Code's `Agent` was named `Task`, so a rule naming `Task` still matches it. An MCP call carries both `mcp__<server>__<tool>` and the bare tool name, with `server` unchanged. An Adapter relays only the names its own harness documents and never invents a cross-harness one: `tool` is the harness's vocabulary, `kind` is the portable one, and a rule naming `WebFetch` is scoped to the harness that calls it that. Because harnesses rename tools and neither carries its aliases into its own hook matcher, a former name is what keeps a rule working across a rename, and handrail is the layer that carries it. A rule that names a tool the running harness never emits simply does not match: handrail cannot enumerate a harness's tools, so it cannot tell a typo from a tool it has not heard of, and reports neither.
- `agent_type` names the subagent a spawn call asks for; `agent_prompt` is the task text it hands over. Both read the tool input: `subagent_type` and `prompt` on Claude Code, `agent_type` and `message` on Codex. Both are single-valued, because a spawn call names one subagent and gives it one task; a harness that ever batches spawns produces one payload per spawn, the shape ADR [0014](adr/0014-one-payload-per-edit.md) already requires for a multi-file patch. `agent_type` holds the harness's own string, relayed and never normalized: subagent definitions are per-repo files on both harnesses, so there is no portable value set to define, and a rule naming a value reaches the harness that uses it.
- `agent_type` on `SubagentStart` and `SubagentStop` is read from the envelope and names the subagent the event is about, the meaning it has on a spawn call. On a tool event inside a subagent the envelope's `agent_type` names the caller, and no canonical field carries it. The Adapter evaluates nothing on a subagent event whose `agent_type` is empty: on Claude Code that is the harness's own internal agent.
- `model` is the model a call asks for, read by key presence from the tool input's `model` key on any tool; both harnesses spell it `model` on their spawn tool. It holds the harness's own string, relayed and never normalized, and is single-valued. It is the model requested, not the model that runs: a subagent definition's `model:`, a Codex role file, `CLAUDE_CODE_SUBAGENT_MODEL` and Codex's `agents.default_subagent_model` each choose a model with nothing on the wire, and a Codex role file overrides the request. A rule on `model` stops an agent asking for a model; the files and settings that choose one without asking are the user's to own. A rule that means spawns only adds `kind: agent`.
- `url` is a destination the call names, read from the tool input's `url` key by key presence on any tool, and by Adapter knowledge where a harness nests it: `ws.url` on Claude Code's `Monitor`, and each `open[].ref_id` on Codex's `webrun` that parses as an absolute `http` or `https` URL. Multi-valued. A domain list (a search filter, a sandbox grant) is never a `url`.
- `domain` is derived from each `url`: the host of a `net/url` parse, lowercased, with port, userinfo, IPv6 brackets and one trailing dot removed. It is never resolved. A `url` that does not parse, has no host, or leaves a host character outside `[a-z0-9.-]` (an IP literal excepted) yields no `domain` and sets `unreadable`, because a host handrail reads differently from the fetcher is a host a rule can be steered past. Internationalized hosts fall under that clause.
- `domain` is the host the call names, not where the fetch ends. A tool that follows a redirect itself reaches a host no rule saw. Shell commands never fill `url` or `domain`: a shell call reaches the network through `command`.
- `network_grant` is a host the call asks the harness's sandbox to open for it, read by Adapter knowledge from `allowed_domains` on Claude Code's `Bash`, `PowerShell` and command-form `Monitor`. Multi-valued. Each entry is lowercased, with any `:port` and IPv6 brackets removed; a leading `*.` is kept. It is never a destination, so it never fills `url` or `domain`, and `WebSearch`'s key of the same name, a result filter, never fills it.
- `unsandboxed` is `true` when the call asks to run outside the harness's sandbox (`dangerouslyDisableSandbox: true` on Claude Code's `Bash` and `PowerShell`), and absent otherwise.
- Both are read in every permission mode. Claude Code honours a grant only in auto mode and ignores it elsewhere, so a rule on `network_grant` also fires on a grant that would have had no effect. In `bypassPermissions` a sandboxed command reaches any host with no tool input asking for it, which no rule sees.
- `removed_content` is the text an edit names as removed: `old_string` on Claude Code's `Edit`, and the `-` lines of an `apply_patch` file section, joined with newlines, without the `-` and without context lines. Like `content` it describes the call, never the file: it holds what the call names, which usually includes text the call puts back. A call that names no removed text leaves it absent: a whole-file `Write`, an `*** Add File:` over an existing file, an `*** Delete File:` (which sets `deletes`), `NotebookEdit`, and a shell command. On Claude Code `old_string` can be part of a line, so a condition sees removed text only when the edit names it whole.
- `response` is the agent's last message on `Stop`, and the subagent's last message on `SubagentStop`, read from the envelope's `last_assistant_message` on those two events only. It is the last message, never the whole turn, and the Adapter trims it. A stop with no text leaves it absent: Claude Code omits the key, and Codex sends `null`, which on this key alone means absent rather than unreadable. The agent writes this text, so a condition on it is one the agent can satisfy or evade by its choice of words.
- A shell call also yields one payload per file its syntax names: the target of each redirect to a file, and each file a listed program names by a fixed grammar over its own arguments. A write or create is a `file_edit` payload and a read a `file_read` payload, each holding that one `path` and the call's per-call fields (`event`, `harness`, `session_id`, `tool`, cwd); `network_grant` and `unsandboxed` stay on the `shell` payload. It holds no `command`, `content`, `deletes`, `writes_empty` or `removed_content`. The `shell` payload is unchanged. The same file named at several wrapping levels is one payload.
- Redirects: `>`, `>>`, `>|`, `&>`, `&>>`, `>&` to a file and `<>` are writes; `<`, `<&` to a file and `<>` are reads. fd duplication, heredocs, herestrings and `/dev/null`, `/dev/stdin`, `/dev/stdout`, `/dev/stderr`, `/dev/tty` and `/dev/fd/*` name no file.
- Listed programs, from Claude Code 2.1.280's own permission table. Write: `rm`, `rmdir`, `mkdir`, `touch`, `tee` (each operand), `cp` and `mv` (the destination: the last operand, or `-t`/`--target-directory`; the sources are reads), `sed` with `-i` (each file operand; without `-i` they are reads). Read: `cat`, `head`, `tail`, `sort`, `uniq`, `wc`, `cut`, `paste`, `column`, `tr`, `file`, `stat`, `diff`, `cmp`, `comm`, `awk`, `gawk`, `mawk`, `nawk`, `strings`, `hexdump`, `od`, `base64`, `nl`, `tac`, `rev`, `fold`, `expand`, `unexpand`, `fmt`, `pr`, `numfmt`, `tsort`, `sha256sum`, `sha1sum`, `md5sum`, `cd`, `ls`, `find`, `jq`, `grep`, `egrep`, `fgrep`, `rg` (file operands after the pattern), `git` (`grep`/`diff` operands, `-C`, `--work-tree`). Each program has a flag table (section 2, Wrappers and nested shells) and honours `--`. A program joins only if a fixed grammar over its own arguments names the file it writes or reads; each entry is a spec change.
- A target or operand holding an expansion, a command substitution, `~user`, a glob or a brace sets `unreadable: path` on its payload and keeps its source text as a best-effort `path`. An unknown flag on a listed program makes every operand its own payload with `unreadable: path`: `file_edit` if the program can write, `file_read` if it only reads.
- On Codex, a shell call in a form Codex itself intercepts as a patch (`apply_patch` or `applypatch` with a literal heredoc, optionally after `cd <path> &&`) yields the per-edit payloads of that patch, exactly as the `apply_patch` tool does, with paths joined to the `cd` path as Codex joins them, beside its `shell` payload. Codex applies that form after the hook with no second hook, so this is the only place handrail sees those edits.
- `raw.*` is a reserved shape for the untouched harness payload. No condition addresses it (section 11), so the engine does not carry it on the hot path.
- `transcript_path` is optional, present only where the harness provides it. Nothing reads it: the Analyzer is a skill, and a skill never sees a hook payload (section 7), and no condition tests the transcript (section 11).

### Outcomes

ADRs: [0019](adr/0019-who-hears-a-rule-fire.md), [0021](adr/0021-ask-is-an-action.md).

Exactly four, ordered `block > ask > warn > allow`, and an evaluation takes the strongest Action among the matched rules across every payload of the event. `allow` is the absence of a match, not an Action. `warn` proceeds, injects the rule's message into the agent's context, and tells the human that the rule fired. `ask` hands the call to the human: it proceeds only if they approve it, with the rule's message shown to them in the approval prompt and injected into the agent's context. `block` denies, with the rule's message as the reason to the agent and to the human. handrail never rewrites a call (section 11).

The order is the gate, not the volume: an `ask` is stronger than a `warn` because a `warn` always proceeds, and a `warn` matched beside an `ask` still delivers its message.

The two audiences read different text, because a rule's body is prose addressed to the agent. The agent always gets that body. The human gets it on a `block` and on an `ask`, where the interruption is theirs and the body is the answer to why, and one line naming the rule on a `warn`, where the same prose at warn frequency is what trains people to stop reading the channel. A rule whose message is coaching rather than alarm sets `agent_only: true` (section 2) and no human line is sent. `Stop` and `SubagentStop` are the one exception: any message to the agent there makes it continue, so a `warn` on them tells only the human (section 2).

handrail decides nothing by default. `ask` is not what handrail does with input it cannot read; it is an Action a rule on `unreadable` may choose, and usually should.

A rule on trial (section 2) is evaluated and recorded but contributes no Outcome and no message, so it can turn none of the four into another. A project whose enforcement state is `off` (section 3) produces no Outcome at all, because no evaluation runs.

## 2. Rule format

ADRs: [0003](adr/0003-rule-file-format.md), [0010](adr/0010-payload-field-semantics.md), [0011](adr/0011-parsed-shell-commands.md), [0012](adr/0012-fail-open-policy.md), [0014](adr/0014-one-payload-per-edit.md), [0016](adr/0016-trial-rules.md), [0019](adr/0019-who-hears-a-rule-fire.md), [0021](adr/0021-ask-is-an-action.md), [0024](adr/0024-how-a-condition-reads-many-values.md).

A Rule is one markdown file, `<rule-name>.md`. Identity is the filename; there is no `name:` field. Matcher in YAML frontmatter, message as the markdown body:

```markdown
---
event: PreToolUse
kind: shell
action: block
conditions:
  - field: command
    matches: rm\s+-rf
  - any:
      - field: command
        contains: " /"
      - field: command
        starts_with: rm -rf /
examples:
  match:
    - command: sudo rm -rf /
  no_match:
    - command: rm -rf ./build
---
Never delete recursively from the filesystem root. If you need to clean a
build directory, name it explicitly and stay inside the repo.
```

- **Matcher**: explicit `event:` (one of the eight event names), optional `kind:` (omitted = all kinds). Only tool events carry a kind: a `kind:` on any other event never matches.
- **Conditions**: implicit-AND list; an entry may be a one-level `any:` group for OR; no deeper nesting. Each condition names one canonical payload field with the operator as the key.
- **Operators**: `matches` (RE2), `contains`, `equals`, `starts_with`, `ends_with`, `glob` (supports `**`); a uniform `not_` prefix negates any. RE2 means no lookarounds or backreferences. Case-sensitive by default; regex opts in with inline `(?i)`; string operators have no case flag. Every operator value is a string: the frontmatter reader reads a scalar as its text with no boolean or number coercion, so `equals: true` compares against `true` and needs no quotes. Example entries and `test --field` values are strings on the same terms.
- **Glob dialect**: Go's `path.Match` plus `**`. `*` and `?` never cross `/`; `[...]` is a character class, negated by a leading `^` (`!` is an ordinary member), and `\` makes the next character literal. `**` skips directories only when it is its own path segment: leading or after a `/`. `**/` matches zero directories too, so `**/*.env` covers a file at the repo root; a trailing `**` matches every depth below. Anywhere else, `**` reads as `*`. Patterns are anchored: a glob matches the whole field, not a substring of it.
- **Candidates**: a canonical field holds one or more Candidates, each written one or more ways, its Spellings. A rule matches when some choice of one Candidate per field makes its conditions true, and a Candidate meets a term when any of its Spellings does. So a positive term matches when anything the call does matches; a `not_` term matches when something the call does has no Spelling that matches, which is how an allowlist reads (`not_starts_with: git` fires on `git status; rm -rf /`); and terms on one field read the same Candidate, so a `not_` term excepts the call the rule's other terms found. Terms on different fields choose independently. A field with one Candidate reads as a single value.
- **What the Candidates are**: for `command`, every statement the program runs, once per wrapping level: with its leading assignments, without them, and once more for each Wrapper or nested shell removed, each level its own Candidate; and every redirect whose target is a file, as written. Each has two Spellings, its source text and its unquoted form. The whole line is a Candidate for positive terms only; a `not_` term never reads it, and when the parse yields no command at all, a `not_` term on `command` matches. For `tool`, one Candidate whose Spellings are every name the call answers to. For `network_grant`, `url`, `domain` and `unreadable`, one Candidate per entry; for `path` on a rename, one per path; a shell call's `path` is always one Candidate, because each named file is its own payload.
- **Shell commands**: the `command` field is a shell program, not a string. handrail parses it with `mvdan.cc/sh/v3/syntax` and a condition asks its question of every command the program runs. `starts_with: rm -rf /` therefore fires on `cd /tmp && rm -rf /`, on `echo $(rm -rf /)`, on `(rm -rf /) && echo ok`, on `if true; then rm -rf /; fi`, on `FOO=1 sudo timeout 30 rm -rf /`, on `bash -lc 'rm -rf /'`, and, through the unquoted Spelling, on `rm "-rf" /` and `rm    -rf   /`. Error recovery is on, so a truncated command still yields the commands it holds. A hard parse failure yields no commands, sets `unreadable: command`, and keeps the whole line as a Candidate for positive terms. Parsing is bash-dialect for every `command`, whatever its payload's kind, PowerShell, zsh and ksh included, which is an approximation: a Windows path such as `C:\ -Recurse` reads the backslash as an escape and merges two words.
- **Wrappers and nested shells**: handrail reads shell syntax and never shell semantics. It follows code into another program only when two things are true: the program is on a fixed list, as a shell or as a Wrapper with a fixed argument grammar, and the code is literal in the call. It never expands a variable, reads a file, follows data from one command into another, or runs anything.
  - Wrappers, each with a flag table (below), stripped with both forms kept as Candidates so a rule can still name the Wrapper itself: `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command` (but not `command -v`), `builtin`, `noglob`, `sudo`, `env`, `exec`, `doas`, `setsid`, `flock`, `watch`, `xargs`, `find -exec`/`-execdir`/`-ok`/`-okdir`, `mise exec --`, `direnv exec DIR`, `devbox run`. `watch` and `flock -c` pass their command to `sh -c`, so their argument is parsed as a script.
  - **Flag tables**: every Wrapper and every listed file program (section 1) has one, kept as data in the code. It gives each flag its arity and at most one effect, taken from the program's upstream documentation; where GNU and BSD ship a program under one name, the table is the union of both. The effects: *supplies the pattern or script*, so no operand does (`awk -f`, `sed -e`/`-f`, `grep` and `rg` `-e`/`-f`), and a file it names is a `file_read` payload; *its argument is a script*, parsed as `watch`'s is (`env -S`, `flock -c`); *sets write mode* (`sed -i`); *names the target* (`cp` and `mv` `-t`). Long options match by unique prefix, as `getopt_long` does. A file program reads flags anywhere before `--`, as GNU's argument permutation does, so `sed 's/a/b/' .env -i` is a write; a Wrapper stops at its first operand, where its command starts. A flag of uncertain arity, one the two implementations disagree on or one the table lacks, is read both ways: taking no argument and taking one, and inside a cluster, ending the cluster and taking its rest. On a Wrapper the readings are the word positions where its command can start, each its own Candidate, so `sudo -X foo rm -rf /` meets `starts_with: rm` and there is at most one Candidate per word. On a file program, the operands of every reading become payloads. An unknown flag also sets `unreadable: command` on a Wrapper, and on a file program it follows section 1. A flag entry is a code change; a program entry is a spec change.
  - Shells: `sh`, `bash`, `zsh`, `dash`, `ksh`, `mksh`, and `su -c`. When a listed shell receives its code as literal text, handrail parses it and adds the commands it finds, exactly as `$()` contents are. Spellings: `-c` and any short-flag cluster holding `c` (`-lc`, `-ec`, `-euc`); `eval` with literal arguments, joined by spaces as bash does; a literal heredoc or herestring fed to a listed shell.
  - When a listed program runs code the call does not hold literally, handrail sets `unreadable: command` and keeps a best-effort reading with each expansion as its source text: `bash -c "$X"`, `sh -c "rm -rf $D"`, `eval "$X"`, a heredoc with expansions, stdin piped or redirected into a listed shell with no script file (`curl ... | sh`, `sh < f`), and an expansion in command position (`$X args`, `$(curl ...) args`). `bash script.sh` is not a give-up: it runs a file, the same as `./script.sh`.
  - Re-parsing stops after four levels; only re-parsing counts, not stripping a Wrapper. A deeper call sets `unreadable: command` and keeps the Candidates already found.
  - A program joins a list only if it runs, on this machine, a command named in its own arguments. Each entry is a spec change. Named limits are in section 11.
- **Absent fields**: a condition against a field the event does not carry never matches, in either polarity. `not_ends_with` on `path` says nothing about a shell command that has no path, so it does not fire there. Narrowing by event and `kind:` is how a rule reaches the calls it means to. A field the call carries empty is absent on the same terms: an empty value is no answer about the field rather than an answer of nothing, so the Adapter never presents one. `content` is not an exception, because presenting the empty string would fire every `not_contains` rule against text nobody wrote, which is the louder mistake and the one that blocks the wrong call. A spawn call whose harness carries no subagent type leaves `agent_type` absent, so a rule shaped as an allowlist (`not_equals` on `agent_type`, action `block`) does not fire on it; the form that does fire is a `kind: agent` condition carrying no `agent_type` condition at all, which blocks every spawn whatever its type. A spawn that names no model leaves `model` absent, so an allowlist written as `not_equals` on `model` does not fire on a subagent that inherits its parent's model or takes one from its definition. A `url` key on an MCP tool fills `url` whether or not the tool fetches it, so a rule meant for fetches narrows with `kind: network` or `tool`.
- **`writes_empty`**: the one fact that absence would otherwise hide. A `file_edit` call that carries a `path` and whose written text was positively read as the empty string also carries `writes_empty` with the value `true`, so `field: writes_empty` with `equals: true` selects it: the call writes no text. On a whole-file write that leaves the file empty. On an edit it removes text and adds none. Claude Code's `Edit` with an empty `old_string` and an empty `new_string` creates an empty file and counts. The signal is derived from the call and never from disk: handrail neither stats nor reads the target, so it does not distinguish truncating a full file from creating an empty one, or removing a line from removing the last line. A key the call omits, a key holding a non-string, and a patch envelope handrail could not parse all leave the field absent, so the signal never stands in for a call handrail failed to read. The absent-field rule governs it like any other field, so `not_equals` on it never fires.
- **`unreadable`**: what handrail could not read, so that a give-up is matchable instead of invisible. It holds one value per failure: a canonical field's name when the call carried the key but not a value of the type handrail expects, or when a shell command or patch envelope would not parse; `command` also when a listed shell or Wrapper runs code the call does not hold literally, or nesting passes four re-parses; `path` when a shell call names a file it cannot read literally; `domain` when a `url` yields no host handrail can trust; `payload` when the harness payload itself would not parse, stdin would not read, or there was no working directory; and `rules` when a rule tier could not be located (no directory can be named for it: no `HOME` and no absolute `XDG_CONFIG_HOME`; a tier directory that does not exist or is empty is located, and sets nothing) or a rule file could not be parsed. The field that failed stays **absent**, so every existing condition keeps its meaning and no `not_` condition fires against a value handrail invented. `command` is the exception: a shell give-up keeps a best-effort reading (Shell commands, above), and when a command would not parse at all the whole line stays a Candidate for positive terms and a `not_` term on `command` matches (ADR [0024](adr/0024-how-a-condition-reads-many-values.md)). A key a harness schema declares nullable reads `null` as absent rather than unreadable; the Adapter lists those keys, and today the only one is Codex's `last_assistant_message`. On a patch, `unreadable` is per edit: a file section handrail cannot read marks its own payload and the others are evaluated. A rule fails closed on a specific gap with `field: unreadable` and `equals: command`, or on any gap with `matches: .`, and `ask` is its usual Action. Two limits are structural: a payload handrail could not parse carries no `kind`, so only a kind-less rule reaches it; and a rule cannot fail closed on its own tier being unlocatable, so the `rules` value reaches a Project-tier rule when the Global tier is missing and reaches nothing when every tier is. An untrusted Project-shared tier is **not** a failure and sets nothing: it is a normal state with its own notice and its own command, and a rule failing closed on it would halt work in every fresh clone.
- **Several edits in one call**: one harness event may produce several canonical payloads. A Codex `apply_patch` envelope naming N files produces N payloads, one per file section, each carrying its own `path`, `content`, `removed_content`, `writes_empty` and `deletes`, and each repeating the call's own `event`, `tool` and cwd; each carries the kind of its own act. Every payload is evaluated and the Outcome is the strongest among them, so no file after the first escapes a `path` or `content` rule. Fields are split this way rather than made multi-valued because `path` and `content` must answer for the same edit: a content condition answering for one file while path answers for another blocks the wrong call. A rename is one payload whose `path` holds both the source and the destination as two Candidates, so a `not_` term on `path` fires when either path fails it. Where a rule matches several payloads its message is delivered once, followed by the files that matched, up to ten and then a count. A file section handrail cannot read carries `unreadable` and does not stop the others being evaluated; an envelope with no recognizable header at all yields one payload carrying `unreadable` and no `path`. The envelope text itself is not addressable: `command` is a shell program, and a patch envelope is not one.
- **`kind: agent`** selects the spawn tools an Adapter knows by name, and is a convenience rather than the coverage. A harness may ship more than one spawn tool, may namespace it configurably, and may let a plugin register another, so a rule that must reach every spawn conditions on `agent_type` and omits the kind.
- **Actions**: `warn` (default), `ask`, and `block`. `ask` is valid only on `PreToolUse`, the one event whose subject a human can approve; on any other event it is a validation error. There is no `defer`: harnesses that offer it use it to suspend a headless session, which is not a guardrail decision, and a rule could not know whether it applied.
  On `Stop` and `SubagentStop`, any message that reaches the agent makes it continue. So there a `block` means "not done": the agent continues once, with the rule's message as its next instruction. When the harness reports `stop_hook_active: true`, handrail evaluates no block rule on that event (trial ones included), so no rule can loop. A `warn` there tells only the human, and `agent_only` on it is a validation error. `block` is a validation error on an event no harness can block: `SubagentStart`, where neither harness can refuse a spawn, and `PostToolUse`, `SessionStart` and `SessionEnd`, where the tool has already run or the event has no decision control. Degradation (section 4) is for a gap on one harness only. A `Stop` or `SubagentStop` rule narrows with `response`; without it, the rule fires at every turn end.
- **Trial**: `trial: true` evaluates the rule and delivers nothing. It matches as it always would and earns a Decision log line naming the action it would have taken, but contributes no Outcome, no message, and no ordering slot: a trial `block` never blocks, a trial `ask` never asks, and a trial `warn` never injects. It is how a new rule is watched before it is trusted, and it is orthogonal to `action` because the point is to leave the traffic unaltered. `action: warn` cannot do this job: its message reaches the agent, which then steers away from the behaviour the trial exists to measure. Degradation never applies to a trial rule (section 4). It is not an Action and cannot be spelled as one.
- **`agent_only`**: `agent_only: true` withholds the human line, leaving the rule's message to the agent's context alone. It is for coaching rules, the ones that fire often and that nobody needs to watch. It says nothing about matching and nothing about the agent's channel, and it is not a quieter trial: a trial rule delivers to nobody and contributes no Outcome, where an `agent_only` rule enforces normally. On a `block` or `ask` rule it is a validation error: a denial whose reason the human cannot see is a support ticket rather than a guardrail, and an `ask` without the human has nobody to ask. It is refused in the Project-shared tier (section 3). For a rule that sets it, the Decision log is the human's only record that it fired.
- **Message**: static markdown, no templating; literal `{{` stays literal.
- **Housekeeping**: `enabled:` defaults to true; `trial:` defaults to false; `agent_only:` defaults to false; no `pattern:` shorthand; no format `version:` field; no sugar aliases.
- **Multiple matches**: every message is delivered labeled with its rule name; the strongest Action among them is the outcome. The human's text travels as one combined message, in the approval prompt on an `ask` and in the harness's user-visible field otherwise, in the same order the agent's messages use (section 3: tier, then alphabetical), one entry per contributing rule: a block's or ask's body, or a label line for a warn that did not opt out.
- **Examples**: optional `examples:` with a `match:` and a `no_match:` list. Each entry is one call, written as canonical fields the way `test --field` takes them; `event` comes from the rule, and so does `kind` unless the rule leaves it unset, when an entry may set it. An Example is evaluated against its own rule alone and asserts that the rule's matcher selects the call, or does not. It never asserts an Outcome, so it passes or fails the same in every project, tier, Trust state and enforcement state. The engine derives from an Example everything it derives from a live call: shell Candidates, nested shells, `domain`, and a command-side `unreadable`. What only the Adapter reports, such as a non-string JSON value, cannot be written. One Example is one payload, so a multi-edit patch is written as separate Examples. A failing Example never changes enforcement: the rule enforces as written. Examples run in `check`, `sync` and `doctor` for every rule file that parses, whatever its state (disabled, on trial, shadowed, dropped or demoted), and at `SessionStart` for every tier in effect, an untrusted Project-shared tier excepted. A failure at `SessionStart` is one notice to the human and the agent naming the failing rules and their count, never an Example's text. An enabled shadow is also tested against the `match:` Examples of the rule it replaces (section 3).
- **Strictness**: strict at sync and at `check`. A validation error fails both: bad YAML; an unknown frontmatter key, condition key, condition field, event, kind or action; a list or map where a single value belongs; zero or multiple operator keys; an invalid regex or glob; a `glob`, `equals` or `not_` form of either on `path` whose value lexical cleaning would change, since no cleaned path can meet it; a missing `event` on an enabled rule or a missing message; `trial: true` on a disabled rule; `agent_only: true` on a `block` or `ask` rule, or on a `warn` on `Stop` or `SubagentStop`; `ask` on any event but `PreToolUse`; `block` on `SubagentStart`, `PostToolUse`, `SessionStart` or `SessionEnd`; `agent_only: true` in the Project-shared tier (section 3); and an Example with an unknown field, a field the rule's event never carries, a `kind` when the rule sets one, no fields, or a key other than `match` and `no_match`. A failing Example is not a validation error: `check` exits 1 on it, and `sync` reports it and still writes. At event time handrail never invents a block: a failure of its own is reported, never enforced, because a hardcoded denial is a policy the user did not write. Reporting means both channels, every time: the harness's user-visible warning field and the agent's context, because a notice only the agent sees is no notice at all when the agent is what the rule exists to constrain. `Stop` and `SubagentStop` are the exception: there the only way to reach the agent is a continuation, which would be a block handrail invented, so every notice handrail sends itself on those events goes to the human alone, and the agent hears only a block rule's message. A rule that cannot be parsed is skipped and named, and so is a rule whose Examples are malformed in any of the ways above. Silent failure is never allowed. What handrail could not read it declares through the `unreadable` field, so a rule, and only a rule, can turn a give-up into a block or an ask.

## 3. Tiers, precedence, trust

ADRs: [0004](adr/0004-rule-tiers-and-precedence.md), [0020](adr/0020-project-shared-is-add-only.md).

| Tier | Location | Notes |
|---|---|---|
| Global | `$XDG_CONFIG_HOME/handrail/` (default `~/.config/handrail/`) | XDG on every Unix platform including macOS. |
| Project-shared | `.handrail/` at the repo root | Committed. Gated by trust. May not replace a Global rule. |
| Project-personal | `.handrail/local/` | Sync appends the ignore line to `.git/info/exclude` when missing. Read as Project-shared when the repository supplies it. |

- Project tiers are discovered at the repo root only: the nearest ancestor of the event's cwd holding a `.git` entry, or the cwd itself outside a repo. Handrail finds that ancestor by walking up itself rather than running `git rev-parse --show-toplevel`, for the same root without a process spawn, which is most of the hook budget, and without requiring git on the machine. Rule directories are then read at that root and nowhere else: no walk-up for `.handrail/`, no monorepo nesting.
- Precedence is most specific wins: Global < Project-shared < Project-personal. Not a security boundary in general: Project-personal outranks both other tiers, and anything that can write the working tree can write it. Exactly one direction is guaranteed: **a Project-shared rule never replaces a Global rule.**
- Scanning is recursive; identity = basename; a duplicate basename within a tier is a sync error; `local/` is excluded from the shared scan.
- A same-named rule in a higher tier **shadows** the lower one wholesale; no field merging. Disabling an inherited rule is a stub shadow containing only `enabled: false`; a disabled rule is exempt from matcher validation, present fields still validate strictly. Re-enabling it is deleting the stub, not setting `enabled: true`: an enabled rule with no `event` fails validation, so the stub cannot be flipped in place.
- An enabled shadow is also tested against the `match:` Examples of the rule it replaces, so a narrowed copy that has drifted from a changed original is reported. A failure is reported as any Example failure is (section 2) and never changes what is enforced. A disabled stub is exempt: switching the whole rule off is its purpose.
- There is no trial stub. Disabling works as a stub because a disabled rule needs no matcher, where a trial rule still has to match, so a `trial:`-only stub would have to borrow the shadowed rule's matcher, and that is the field merging this tier model refuses. Trialling an inherited rule means copying it into your tier, which is what shadowing means everywhere else.
- **One tier pair is excluded: a Project-shared rule may not shadow a Global one.** The collision drops the shared file: the Global rule stands, `check` and `sync` name both paths with the reason, `check --json` carries `dropped_by`, a `SessionStart` notice names the count, the hot path stays silent, and the exit code stays 0. Never a validation error, because the collision needs a Global file the repository's author cannot see, so `check` would fail a user on a repository they did not write and cannot fix. The shared tier is therefore **add-only** against Global: it may add rules of its own, including stricter ones under names of their own. Dropping a shared `enabled: false` stub can deny a call that previously passed; that block comes from a rule the user wrote, which is the condition ADR [0012](adr/0012-fail-open-policy.md) sets. Project-personal carries no such restriction and shadows both lower tiers.
- **A Project-shared rule may not carry `agent_only: true`**, shadow or not: a repository rule that injects into the agent's context without telling the human is the objection ADR [0019](adr/0019-who-hears-a-rule-fire.md) raises. `check` and `sync` error; the hook path drops the field and reports it, which only makes the rule louder. `trial: true` on a Project-shared rule is permitted, since it weakens nothing the user had.
- **A tier's identity is its supply, not its path.** `.handrail/local/` is Project-personal only where it is genuinely local. It is read as Project-shared, and so gated by Trust and bound by the add-only rule above, when any path under it appears in the git index, or when `.handrail` or `.handrail/local` is a symlink. `.git/info/exclude` cannot prevent this: git ignore rules never apply to a path already in the index, so a repository that commits `.handrail/local/` would otherwise ship every cloner an ungated, top-precedence tier. The check runs only where `.handrail/local/` exists: an `lstat` on each of the two paths, then an in-process read of `.git/index` that stops at the first entry past `.handrail/local/`, which index order puts near the top, so it costs microseconds at any repository size and spawns no process (section 10). The reader covers every index format git writes: v2, v3 extended flags, v4 prefix compression, a sparse-index directory entry covering the prefix, SHA-256 object names, a linked worktree's own index, and a split index.
- A repository cannot ask for a relaxation. It could only name a Global rule it cannot see, or a call, which would make it an allowlist. The user relaxes a Global rule in one repository with a Project-personal shadow: a copy with one added exception, or the `enabled: false` stub.
- Nothing above constrains a *write* to a rule directory. An agent that can write the working tree reaches every project tier, and one that can write the home directory reaches Global. handrail's answer is a pair of handrail rules the add skill teaches and handrail neither ships nor hardcodes: a Global `PreToolUse` rule on `kind: file_edit` whose `path` is under `**/.handrail/**` or the Global directory, and one on `kind: shell` whose `command` names either, both with `action: ask`. `ask` rather than `block`, because handrail's own skills run as the agent and write rules through the same tool calls: the human approves each write, and that approval is the only grant a relaxation needs. On Codex `ask` degrades to `block`, and the skills print the file instead of writing it. The add skill also teaches a `block` rule on `kind: file_edit` for handrail's state directory, which holds the trust registry, the Decision log grant, the enforcement state and the Decision log.
- **Merging happens in the engine at event time.** Sync writes exactly one stable hook entry per event into each harness's user-level config and nothing into project config. The entry carries no `matcher` and no `if`: sync's output depends on no rule, so a rule takes effect on the next event without a re-sync, and no harness-side filter can skip a call a rule would have matched. Sync is per-machine: once synced, every repo with a `.handrail/` directory is enforced.
- **Trust**: an engine-side, path-once registry (XDG state dir) gates the Project-shared tier. In an untrusted repo the shared tier is skipped and a one-line notice pointing at `handrail trust` is injected. Global and genuinely local Project-personal tiers are never gated.
- Message ordering on multi-match: tier order (Global, Project-shared, Project-personal), then alphabetical within a tier.
- Claude Code cloud sessions read neither user settings nor a local binary: unenforced.

### Enforcement state

ADR: [0017](adr/0017-enforcement-state.md).

Suspending a guardrail on purpose is a normal act, and handrail's answer is one switch rather than an edit to every rule.

- **Three states**: `enforce` (the default), `trial`, and `off`. `trial` puts every rule on trial, including rules already there. `off` skips evaluation entirely: nothing matches, nothing is logged, nothing fires, because a suspended guardrail should not be journaling the calls it let through.
- **The weaker state applies**, ordering `off < trial < enforce`. A rule's own `trial: true` is never overridden upward, so the switch only ever loosens.
- **Per project, keyed by Project root**, in the same path-once XDG state registry as Trust and the Decision log grant. `--global` sets a machine-wide state instead, applying wherever no project state does.
- **Loud while it is not `enforce`.** Every `SessionStart` in an affected project tells the human and the agent the state and its scope, and the state appears in `check`, `sync`, `doctor`, and `mode`. The state does not expire, so this notice is what stands between a suspension and a project that looks guarded and is not.
- **It is not a boundary.** Anything that can run `handrail mode off` can suspend handrail. `mode` refuses when a harness session id is present in the environment (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`) and points the user at their own terminal, which is a speed bump against an agent switching the tool off mid-session and is defeated by `env -u`. The `SessionStart` notice is what makes such a switch visible afterwards.

## 4. Architecture

ADRs: [0002](adr/0002-claude-code-event-vocabulary.md), [0018](adr/0018-one-enforcement-path.md).

One Go binary; the Adapters live in one internal package, `harness`, one value per harness. Both harnesses read the same Claude-shaped hook config and speak the same payload and decision protocol, since Codex's hooks engine is Claude-compatible by design, so they differ by a set of facts (config path, event capabilities, tool names, quirks) and a package apiece would be two copies of one Adapter. Sync writes each harness's native hook config: one entry per canonical event, invoking `handrail hook <harness> <event>` with the harness named explicitly. No runtime harness auto-detection. That single invocation evaluates all matching rules across all tiers.

handrail has one enforcement path, the hook path. It never translates a rule into a harness's own permission or execpolicy syntax, and `doctor` reports when its hooks would not run (section 6). Its hook is synchronous, because Claude Code shows the human no message from an asynchronous hook.

### Capability matrix

Hardcoded in Go per Adapter, next to its translation knowledge. Per-event: exists, can block, can carry a human-visible message. Global flags: context injection, transcript access, fail-open on hook error, fail-open on timeout. Where the two Adapters differ, the fact is a per-Adapter flag in code; where they agree it is engine-wide behaviour, and prose quirks are reported at sync and by `doctor`. The matrix:

| Capability | Claude Code (`claude`) | Codex CLI (`codex`) |
|---|---|---|

| Block on PreToolUse | Yes: exit 0 with `permissionDecision: "deny"`, the reason in `permissionDecisionReason`, the human text in `systemMessage` | Yes: the same JSON deny |
| Ask on PreToolUse | Yes (`permissionDecision: "ask"`). Prompts in every permission mode, `bypassPermissions` and `dontAsk` included; a settings `deny` rule still wins. Headless `-p` with no prompt tool resolves it as a deny, with the reason to the model; the SDK and `--permission-prompt-tool` hand it to the host. Another PermissionRequest hook may answer it | No. Codex rejects `ask` as unsupported and fails open, running the call and dropping `additionalContext`, so the Adapter never emits it and an `ask` rule blocks (section 4, Degradation). No hook can reach Codex's approval flow |

Codex's hash-based hook trust prompts once per entry change; the stable one-entry-per-event shape (section 3) keeps that to a single approval.

handrail evaluates the input the harness hands its hooks. Another hook may rewrite that input (`updatedInput`), and the rewritten call runs without handrail seeing it; the harness's own permission rules still check it. A handrail `block` still holds, because a deny discards every rewrite. Claude Code's managed hooks are the exception: they run before the others, so handrail evaluates their rewrite.

An `ask` is as strong as the harness's approval path: any other PermissionRequest hook can approve it without the human. `doctor` reports such a hook; handrail does not detect or override one at event time.

### Degradation

When one harness lacks a capability a rule needs and the other has it, substitute the nearest action that keeps what the rule promised, never silently. An Action neither harness can deliver on an event is a validation error instead (section 2), so degradation never applies to `block` on `PostToolUse`, `SessionStart`, `SessionEnd` or `SubagentStart`. For `block` that is the strongest available action below it: `warn`, then skip. For `ask` it is `block`: an `ask` promises that the call does not proceed without a human yes, and on a harness that cannot ask, the only action keeping that promise is a denial. This is the one substitution that tightens, and its reason tells the agent and the human that the rule wanted approval and this harness cannot ask for it. A rule on an event a harness lacks is skipped there. Reported per harness at sync time and reprintable via `doctor`; the runtime hot path stays silent. Fail-open quirks are reported in the same place.

A trial rule is never degraded and never appears in the report: it asks the harness for neither blocking nor injection, so there is no capability to substitute for.

An audience is not an action. Where a harness or one of its events carries no user-visible field, the rule enforces unchanged and the agent still hears it; sync reports per harness which events cannot tell the human, beside the action downgrades, and `doctor` reprints it. On `SessionEnd`, which no harness accepts the field on and whose stderr Claude Code renders to the user, the human line goes to stderr, which is the substitution the engine already makes there for a different reason.

## 5. Decision log

ADR: [0015](adr/0015-decision-log.md).

handrail records what it decided, never what the agent did. The harness's own transcript already holds every tool call with its arguments in full, so a second copy of that traffic would cost an append on every event and add nothing. What the transcript does not hold, on Codex at all and on Claude Code only in a format its documentation calls internal and unstable and deletes after thirty days, is which rules matched and why. That is the log's content.

- **Off until granted.** `handrail log on` records the Project root in the XDG state dir, one path per line, the same path-once shape and the same `0600` posture as Trust. Nothing is written in a repo that never asked. The grant is read only when a line is about to be written, so a no-match invocation performs no I/O at all.
- **One file**, `$XDG_STATE_HOME/handrail/log.jsonl`, holding every granted project, each line naming its own root. With no state directory there is no grant and therefore no log.
- **A line per evaluation, not per event.** One harness event produces one or more payloads (section 1), and a line describes one payload's evaluation. Lines from one event share a timestamp and a session id.
- **What earns a line**: an evaluation in which a rule matched, and one in which `unreadable` was set. Nothing else. An untrusted Project-shared tier is not a failure and earns no line: it is a normal state that holds on every event in a fresh clone, and recording it would reintroduce the per-event write this design exists to avoid. A trial rule's match earns a line wherever it fires, whether or not the project holds a log grant: writing `trial: true`, or running `handrail mode trial`, is the request the grant otherwise stands in for, and a trial that records nowhere is both silent and pointless. An `off` project writes nothing, because nothing is evaluated.
- **Fields**: `time`, `version`, `harness`, `event`, `session_id`, `root`, `cwd`, `kind`, `tool`, then `outcome` with `matched` (each entry a rule name, its tier, its action, and whether it was on trial and by which route: the rule's own `trial: true` or the enforcement state), or `unreadable`, or both. The canonical payload rides under `payload` as the engine derived it. The rule's message is not recorded: it is static text in a file `check` prints, and a copy in every line ages the moment the rule is edited. An action downgraded by degradation (section 4) is named on the entry it downgraded. An `ask` line records the outcome `ask` and never the human's answer, which is in the harness transcript.
- **Unredacted, on purpose.** The same command already sits in plaintext in the harness transcript and in shell history on the same disk, so redacting here reduces exposure by nothing and buys a secret corpus to maintain. ADR 0015 names the condition that reverses this, and how the Analyzer's reading of the log stays inside it.
- **Bounded.** Each value is truncated at 512 bytes and each line at 4 KiB, with the truncation marked; anyone needing the untruncated payload has it in the harness transcript. A line is one `O_APPEND` write with no lock and no `fsync`: concurrent sessions in one repo interleave cleanly at that size in practice, the stated ceiling is that POSIX guarantees only that appends do not clobber each other's offsets, so a short write under disk pressure could split a line, and a crash may lose the last line. Over 5 MiB the file rotates to `log.jsonl.1`, keeping exactly one generation. The three numbers are assembly-time calls, like section 10's budget, and move if the numbers say so.
- **Read surfaces**: `handrail log` prints lines, `log --rule NAME` keeps one rule's lines, and `check --stats` summarizes history per rule (section 6).
- **Never enforcing.** A log write that fails is reported like any failure of handrail's own (section 2, Strictness), and never changes an Outcome.

## 6. CLI surface

ADRs: [0006](adr/0006-cli-and-plugin-surface.md), [0015](adr/0015-decision-log.md), [0017](adr/0017-enforcement-state.md), [0018](adr/0018-one-enforcement-path.md), [0022](adr/0022-repo-survey.md). Eleven commands; harness identifiers are the harness's binary name (`claude`, `codex`).

| Command | Does |
|---|---|
| `sync` | Validate via `check`'s logic, Examples included (a failing Example is reported and the hooks are still written), detect installed harnesses (`~/.claude`, `~/.codex`; `--harness` to scope), write each native config, print the annotated effective ruleset and the degradation report, including which events cannot tell the human. |
| `hook <harness> <event>` | The entrypoint sync installs. Payload JSON on stdin, exit codes per the harness protocol. Visible in help, documented as not for humans. |
| `check` | Strict-validate all tiers; print the annotated effective ruleset (tier, shadowing, disabling, trial, and dropped or demoted files per rule). Runs every rule file's Examples and exits 1 when one fails. An untrusted Project-shared tier is validated and its Examples run like any other tier's, and an error or failing Example there exits 1; its rules are absent from the effective ruleset, and `check` says so on stderr, pointing at `handrail trust`. The authoring-time surface: adding a rule needs no re-sync. `--stats` adds, per effective rule, its Decision log history for this Project root across both generations: match count, distinct sessions, first seen, last seen, zeroes included, plus `unreadable` counts per tool and field and the time of the oldest line. No rate: the log records no non-matches. With no grant, `--stats` reports that and prints the ruleset alone. |
| `test <event> [--kind] [--field key=value]... [--stdin] [--harness]` | Dry-run: for each payload the event yields, the shell Candidates grouped with their Spellings (the whole line marked as read by positive terms only), anything handrail could not read, and the matched rules with tier and action; then the final outcome, and the human line verbatim as it would be sent, since who hears a rule fire is otherwise invisible until it fires. Exit 2 on block, 3 on ask. Matched trial rules are listed and marked, and contribute nothing: a trial block rule leaves the reported outcome `allow` and the exit code 0, because what `test` reports is what `hook` does. Under a non-enforcing state, `test` reports the ruleset's own outcome, names the state and says `hook` would deliver nothing under it, since an authoring surface that reported only `allow` would answer nothing. `--stdin` reads a harness payload as that harness sends it and normalizes it the way the hook path does, so what test reports is what hook does; `--harness` says whose payload it is, defaulting to `claude`. The payload's own cwd is discarded: tier discovery starts from the working directory. An untrusted Project-shared tier is skipped, as on the hook path, and named. |
| `trust` | Grant the current repo's Project-shared tier (path-once registry). |
| `log [on\|off] [-n N] [--all] [--rule NAME] [--json]` | The Decision log (section 5). With no argument, print this project's recent lines, newest first; `-n` bounds the count, `--all` widens to every granted project, `--rule` keeps only lines where NAME matched, `--json` emits the stored lines verbatim. `on` and `off` grant and revoke this Project root. |
| `mode [enforce\|trial\|off] [--global]` | The enforcement state (section 3). With no argument, print this project's state and its scope. `handrail on` and `handrail off` are aliases for `mode enforce` and `mode off`. Refuses when run from inside a harness session. |
| `import hookify [path]` | One-shot upstream-hookify converter (section 8). |
| `doctor` | Offline-only: binary location and version; per harness, hook entries present, current, pointing at an existing executable, **not narrowed** (a handrail hook carrying `if`, or a handrail group carrying `matcher`), and **not disabled** (`disableAllHooks` after settings precedence, `allowManagedHooksOnly`, Codex's `[features] hooks = false`); the current repo's tier discovery, supply check, trust state, `local/` exclusion line, Decision log grant with the log's path and size, and enforcement state with its scope; a rule validity summary with the count of rules on trial; every rule file's Examples, an untrusted Project-shared tier included; the degradation report. Exit 1 when any check fails. It also reports, without failing, any PermissionRequest hook active for the current Project root, since one can approve a handrail `ask` without the human. |
| `survey` | Read the current Project root for Repo signals and print them as JSON: per signal, a stable id, the literals found, and the path each was read from, plus every instruction file found at the Project root and in the user's harness directories, each with its class (`user`, or `repo` where git tracks it or it sits in the repository, an untracked `CLAUDE.local.md` excepted), following Claude Code's `@` imports to four hops outside code spans; the managed policy file is never listed. Never lists the tree and never reads a lockfile's content: signals are found by named stats and by matching patterns against `.git/index` read in process, the reader the supply check uses (section 3). Writes nothing, spawns no process, makes no network call, exits 0 on zero signals. The Surveyor is its reader, so it has no human output. |
| `version` | Version, commit, date (GoReleaser-injected). |

- **`--json`** on `check`, `test` and `log`; `survey` prints JSON only.
  - `test`: `{outcome, matched: [{rule, tier, action, message}]}`, where `outcome` is one of `allow`, `warn`, `ask`, `block`. The object also carries what the human-readable output prints: per payload, the Candidates with their Spellings and `unreadable`; the human line; trial marks; and the enforcement state.
  - `check`: `{rules: [{rule, tier, event, kind, action, enabled, trial, shadowed_by, dropped_by, demoted_from, path, examples: {passed, failed: [{expect, fields}]}}], errors: [{path, message}]}`. `dropped_by` is the Global rule whose presence dropped a shared file, else null; `demoted_from` is `"project-personal"` where the supply rule applied, else null; `tier` always reports the effective tier; `expect` is `match` or `no_match`. `--stats` adds the history above.
  - `log`: the stored lines verbatim.
- **Exit codes**: 0 success; 1 usage, internal, or validation error, or a failing Example (`check`, `doctor`); 2 blocked (`test`); 3 ask (`test`). `hook` exits 0 and carries every decision in its JSON, except on `SessionEnd`, where it exits 2 with the human line on stderr (section 4).
- Deliberately absent: `init`, `add`, `list`, `enable`/`disable`, `advise`, per-file `validate`, CLI `analyze` (analysis needs an LLM).

## 7. Plugins

ADRs: [0006](adr/0006-cli-and-plugin-surface.md), [0007](adr/0007-analyzer-design.md), [0022](adr/0022-repo-survey.md).

Both harnesses get a native plugin with full parity: an add skill, an analyze skill, a survey skill, and a SessionStart bootstrap hook. Skills are authored once in one `skills/` tree that both plugins ship: the Codex manifest points at it explicitly, the Claude Code manifest picks it up by convention. The Codex plugin uses the handrail repo as its own marketplace (`.codex-plugin/plugin.json`, `hooks/` directory for the bootstrap); its one caveat is Codex's one-time trust review for non-managed plugin hooks.

Every skill that writes a rule keeps the replay that proved it as Examples (section 2), and no skill reads another rule's Examples as evidence of coverage: coverage is a `test` run against the live ruleset. The skills run as the agent, so on Codex, where the taught rule-directory guard's `ask` degrades to `block`, they print a rule file and its path for the human to save (section 3).

- **`/handrail:add`**: describe a guardrail in words; the skill writes the rule file and runs `handrail check`. It writes the replay that proved the rule as a `match` Example and its near-miss as a `no_match` one. When a Global rule blocks a call that is legitimate in one repository, it relaxes it there with a Project-personal shadow, offering a copy with one added exception before the `enabled: false` stub, and it teaches the guard rules of section 3.
- **`/handrail:analyze`** (the Analyzer): on demand only; no automatic session-end analysis, no nudge hook. It reads two sources. The current session's transcript: `transcript_path` is a hook-payload field and a skill never sees one, so the skill resolves the file from the session id the harness exports (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`); both were confirmed present in the shell environment of a tool call. And, where the Project root is granted, the Decision log, as statistics from `handrail check --json --stats` and as one rule's lines from `handrail log --rule NAME --json` when a proposal is about that rule, with the number of lines pulled reported to the user. It never parses a harness's own record of hook results. It has three jobs:
  - **New rules** for behaviors worth preventing, skipping what the effective ruleset already covers. Signal categories (non-exhaustive): explicit user corrections, repeated instructions, manual reverts and interventions, near-miss dangerous actions.
  - **Tuning existing rules.** The signal is the override: a rule matched, and the user then asked the agent for the act anyway. A rule whose matcher missed a call it was plainly written to catch gets a proposal that widens it. Frequency alone proposes nothing, and a rule with no match proposes nothing beyond one line naming the window, because a guardrail that never fires is usually working.
  - **Concluding trials**: each `trial: true` rule's matches, with a proposal to promote it or drop it.

  Each proposal is a complete rule draft with rationale and evidence. Nothing is written without per-rule approval. A proposal that weakens gets a heavier bar, decided by the act and never by the Analyzer's description of it: editing or deleting an existing rule file, a new rule whose name shadows one in a lower tier, or any rule setting `enabled: false`, `trial: true` or `agent_only: true`. Such a proposal quotes its log lines verbatim and is approved alone. Retiring an editable rule is first offered as a downgrade to `trial: true`; an inherited rule can only take an `enabled: false` stub or a wholesale copy (section 3). Before proposing any rule, the Analyzer checks `--stats` for the field it depends on appearing `unreadable` on that tool, and carries the caveat into the proposal. On approval the skill writes the file, validates with `check`, and replays the motivating event through `test`: a new rule must match its incident, an amended rule must no longer match its. The replay uses the transcript's full tool input where the incident is in this session, else the log payload; a truncated payload with no transcript copy is not replayed, and the skill says so. It writes the incident as a `match` Example, minimized to the smallest input that still matches and with no credential copied; on an amendment, the incident the rule must stop matching moves to `no_match`. Suggested tier: Project-personal by default, Global when clearly project-agnostic; Project-shared stays a manual act. With no grant or an empty log, the skill does the transcript job in full and says once that it could not see rule history. Claude Code writes the transcript asynchronously, so the Analyzer tolerates a slightly stale tail. Harnesses without transcript access lack the feature; the fallback is describing the incident to `/handrail:add`.
- **`/handrail:survey`** (the Surveyor): on demand only, with no hook and nothing unprompted. It proposes rules from Repo signals, reading `handrail survey` for the facts and the prose files that output names. It proposes only from a closed list of signals ([the repo-signals research](https://github.com/svyatov/handrail/blob/research/repo-signals/docs/research/repo-signals.md), 17 signals giving 19 rules), plus prohibitions stated in repo prose (every project instruction file either harness loads at launch: `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/rules/**/*.md`, `AGENTS.md`, `AGENTS.override.md`; and `CONTRIBUTING.md`); a requirement, being a claim about a sequence of events, is never transcribed. A signal enters the list by a spec change with a replay against a real payload and a near-miss, never by the model's judgment in a session. A Repo signal fixes the matcher and never the action, the tier, or whether the rule should exist, so proposals come in three grades, ordered first to last: transcribed prose, proposed as a draft; a fact-determined matcher with a conventional policy, proposed as a draft whose action the user picks; and fact-parameterized taste, asked as a policy question before any draft is shown. Every rule body is written by the skill; repo prose appears only as quoted evidence, attributed to the file it came from. When asked, and never on a plain run, it also proposes from the user's own instruction files: `~/.claude/CLAUDE.md`, `~/.claude/rules/*.md`, the global Codex file under `$CODEX_HOME` (`AGENTS.override.md` if it is not empty, else `AGENTS.md`), and an untracked `CLAUDE.local.md`. A file's class comes from its supply, never its name or the file that imports it: a file git tracks is repo prose. Proposals from the user's files suggest Global, or Project-personal for `CLAUDE.local.md`, and say that a Global rule applies in both harnesses. The instruction file is never edited: the sentence stays as what the agent reads before it acts. A prose sentence becomes a rule only when it is a prohibition, the prohibition is a test on one call's canonical fields, and the matcher never fires on an act the sentence itself allows; a sentence whose stated exception cannot be expressed is dropped. A rules file's `paths:` frontmatter becomes a `path` condition on the draft. Before a proposal is shown, its positive payload, built from the literal the signal found, goes through `test`: a live rule matching it at the same action or stronger means the proposal is skipped and listed as covered, and a weaker match is proposed with the existing rule named. Nothing is written without per-rule approval. The answers are approve, trial, or drop, and the Grade 2 question offers `block` and `warn` in place of approve. On approval the skill writes the file, validates with `check`, and replays twice: the positive payload must match, and a real neighbouring file from the repo, or for a transcribed sentence the closest act the sentence allows, must not. Both payloads are synthetic and the skill says so, and it writes them as the rule's `match` and `no_match` Examples; a rule offered at Global carries no repo literal in its Examples. A proposal lands enforcing unless the user picks trial. Suggested tier: Project-personal by default, Global when the matcher holds no literal from this repo; Project-shared is never written and is named once as a manual step. The Surveyor proposes guards only: a Repo signal never proposes relaxing a rule, even when its literal collides with one. A re-run offers declined proposals again. Zero proposals is a valid result.
- **Bootstrap**: the plugin pins a binary version. On miss or pin mismatch, SessionStart downloads the matching GoReleaser artifact for the OS/arch from GitHub Releases, verifies sha256 against the release's `checksums.txt`, installs to `$XDG_DATA_HOME/handrail/bin/handrail` (PATH untouched; sync writes absolute paths into hook entries), and after a fresh install runs `handrail sync` once. After a fresh install it also tells the human, on `systemMessage`, that `/handrail:survey` proposes rules for the current repo and, when asked, from their own instruction files. It says this once per install, never once per session, and never in the agent's context. A PATH-installed binary (brew, `go install`) is respected and never overwritten. Exec-bit survival and per-arch selection in plugin installs are undocumented upstream: verify empirically during implementation.

## 8. Importer

ADR: [0008](adr/0008-hookify-importer-mapping.md).

`handrail import hookify [path]` converts upstream hookify's `.claude/hookify.*.local.md` files into Project-personal rules (`.handrail/local/`). Upstream semantics were verified against the plugin's engine source.

| Upstream | handrail |
|---|---|
| `event: bash` | `PreToolUse` + `kind: shell` |
| `event: file` | `PreToolUse` + `kind: file_edit` |
| `event: prompt` | `UserPromptSubmit` |
| `event: stop` | `Stop`, where a block continues the agent once (section 2) |
| `all` (default) | Inferred from condition fields; skipped when fields span more than one event |
| `command` | `command` |
| `file_path` | `path` |
| `new_text`, `content` | `content` |
| `user_prompt` | `prompt` |
| `regex_match` | `matches`, with `(?i)` prepended (upstream compiles IGNORECASE), RE2-validated |
| string operators | Verbatim (upstream is case-sensitive already) |
| `pattern:` shorthand | Expanded using upstream's own field inference |

Inexpressible constructs are skipped with a per-rule report naming the reason and the original path; nothing broken is ever written: `old_text`, `transcript`, `reason`, non-RE2 patterns, unmappable `tool_matcher` values, ambiguous `all` rules. A skipped `transcript` condition's report names `response` as the nearest field, which holds the agent's last message only. The converted filename comes from the upstream `name:` field; an existing target is never overwritten (re-runs are safe); originals are untouched; `enabled: false` survives. Upstream has no trial state and no Examples, so the importer writes neither.

## 9. Repo layout, toolchain, distribution

Decided in [the Go stack research](https://github.com/svyatov/handrail/issues/5); findings on `research/go-cli-stack`. Dependency decision: ADR [0011](adr/0011-parsed-shell-commands.md).

- Go 1.27; module `github.com/svyatov/handrail`; root `main.go` + `internal/` packages. One third-party runtime dependency, `mvdan.cc/sh/v3/syntax`, whose own imports are the standard library only. The shipped artifact is a single static binary. The dependency count is a budget kept small rather than a number kept at zero, and `depguard`'s allow list is how it stays a budget.
- CLI parsing: stdlib `flag`, one `FlagSet` per subcommand, manual dispatch.
- Cold start: minimal import graph, no work in `init()`, `CGO_ENABLED=0`, `-ldflags "-s -w"`.
- Lint: golangci-lint v2, a curated set rather than `default: all`, configured in `.golangci.yml`. Two linters turn a rule stated in this spec into a build failure: `depguard` allows only `$gostd`, this module and `mvdan.cc/sh/v3` outside `_test.go` (plus `github.com/rogpeppe/go-internal` inside it), and denies `os/exec` outside `_test.go`, so no command spawns a process (section 10); `forbidigo` forbids `os.Exit` everywhere but `main.go`, which keeps `run()` returning an exit code and therefore testable. Formatters: `gofumpt` and `goimports`.
- Tests: testscript over the compiled binary is the primary seam, `testdata/script/*.txtar`; table-driven subtests under `internal/` only for what a process boundary cannot produce ([ADR 0009](adr/0009-testing-strategy.md)). Commands live in `Taskfile.yml`: `task test` (`go test -race -shuffle=on ./...`) and `task cover`.
- CI: `.github/workflows/ci.yml` on push to `main` and every pull request. The test job runs on ubuntu and macos and fails under 95% statement coverage; the lint job runs on ubuntu. The release build (`CGO_ENABLED=0`, `-ldflags "-s -w"`) runs there too, so a broken one fails on the pull request rather than on the tag.
- Release: GoReleaser v2 (`version: 2`, `homebrew_casks` pipe, `checksums.txt`) on tag push via GitHub Actions; goarch `[amd64, arm64]`, goos `[darwin, linux]` (Windows is a non-goal, section 11). Each archive ships an SPDX SBOM beside it (`<archive>.sbom.json`, written by syft), and every archive, SBOM, and `checksums.txt` carries a GitHub build-provenance attestation, verified with `gh attestation verify <file> --repo svyatov/handrail`. The release body is the tag's `CHANGELOG.md` section, cut by `scripts/release-notes.sh` and passed to `goreleaser --release-notes`, so a tag whose section is missing fails the release before anything is published; `task release-check` runs the same script against the pinned version, which moves that failure onto the pull request.
- Distribution: GitHub Releases + `go install` + Homebrew tap (`svyatov/homebrew-tap`). Install script, winget, scoop, nfpm: only if demand appears.

## 10. Performance budget

No daemon; a plain fast binary (settled during charting). Measured in [the hot-path research](https://github.com/svyatov/handrail/blob/research/hot-path-budget/docs/research/hot-path-budget.md): a no-match `handrail hook` takes 4.7 ms with 50 rules on an Apple M1 Pro, of which 1.9 ms is the operating system's process spawn. The budget is structural plus one acceptance bar:

- Structural: the section 9 constraints (minimal import graph, no `init()` work), and two more. No command spawns a process, the hook path above all: `depguard` denies `os/exec` outside `_test.go`. No read on the hook path grows with the repository: the Project-personal supply check (section 3) reads `.git/index` in process and stops at the first entry past `.handrail/local/`, which index order puts near the top, so it costs microseconds at any repository size where `git ls-files` costs 5 to 20 ms. The Decision log append is one `O_APPEND` write with no `fsync`.
- Acceptance bar: each of three invocations completes in under 20 ms median, cold, on typical developer hardware: a no-match `handrail hook` (read stdin, discover tiers, check supply, parse rules, evaluate, exit); a hook that matches a rule and appends a Decision log line; and a `SessionStart` that runs every Example in effect, which is why Examples need no version gate. A test at the same seam enforces this: it builds the release binary, spawns it repeatedly against a populated three-tier fixture inside a git repository whose `.handrail/local/` exists, and fails when a median crosses the bar. It is a test rather than a `Benchmark`, so CI fails on a regression instead of merely reporting one. 20 ms is four times the measurement; tighten it if the numbers say so, and loosen it only to four times a slower runner's measured median.

## 11. Non-goals and named limits

Named so their absence reads as decided, not forgotten.

### Non-goals

- Harnesses beyond Claude Code and Codex CLI. The project can test those two and no others, so support for any other would be a claim nobody can verify.
- Windows, for the same reason. [The Windows research](https://github.com/svyatov/handrail/blob/research/windows-support/docs/research/windows-support.md) costs it, if it is ever reopened as a new effort.
- Rule packs or sharing beyond a single repo. Guardrails are individual to a repo and a person; the replacement is repo-aware proposal (section 7).
- Cloud-session enforcement: cloud sessions read neither user settings nor a local binary.
- CLI `analyze`: analysis needs an LLM, so it stays a skill.
- Native promotion in any form. handrail has one enforcement path, the hook path, and does not translate rules into a harness's own permission or execpolicy syntax. An entry would be a second decider handrail cannot suppress at event time, blind to tiers, and it defends one vector (`disableAllHooks` in a committed settings file) that it raises the price of rather than closes. `doctor` detects that vector instead. See ADR [0018](adr/0018-one-enforcement-path.md).
- Input rewrite. handrail refuses, asks or warns, and never changes the call. A guardrail's fix has to win against the hooks installed beside it: on both harnesses a deny outranks every other hook, while a rewrite (`updatedInput`) wins only by being the last one taken, so a rewrite that loses runs the original call unchanged and says nothing. A rule that wants a different command blocks and names it in its message. Reopens if a harness gives a hook's rewrite the precedence a deny has.
- `raw.*` conditions. Reserved shape, not plumbing: the harness payload rides along untouched so normalization never loses information, and nothing addresses it. Its motivating cases were named fields rather than an open set, and each was answered by a canonical field. It reopens when a rule exists that no canonical field can express.
- A condition on the transcript. It needs disk I/O on a format Claude Code calls internal and unstable, and the agent can write the words into it. Reopens when a harness documents a stable transcript format.
- `defer` as an Action (section 2).
- Prompt-injection detection: it needs either a rewrite of matched content, refused above, or a classifier, which breaks the one-binary promise.
- Package-install control by package age: it needs a network lookup on the hot path. A rule over `command` already names a package.
- A condition on which agent makes a call (the caller's `agent_type` on tool events).
- A Decision log that leaves the machine, which would make redaction handrail's job (ADR 0015).
- An interrupt channel.
- Unasked refinements: field-level merging in Shadowing, content-bound Trust, monorepo nesting, message templating, per-file `validate`, and search fields (`Grep`/`Glob` `pattern`, `WebSearch` `query`).

### Named limits

- **The hook path is best-effort.** Every bypass in the section 4 matrix switches handrail off; `doctor` reports the ones it can see.
- **Shell**: `fish` and `pwsh` code is not parsed; zsh, ksh and PowerShell are parsed as bash, and so is a `command` on a non-shell tool, so one written in SQL or another language that does not parse sets `unreadable: command` and a fail-closed rule with no `kind:` fires on it. Commands run by a remote runner (`docker exec`, `kubectl exec`, `ssh`) or a package runner (`npx`), and code in a file (`bash script.sh`, `source f`, `npm run`, `make`), are not read.
- A rule whose positive term on `command` only the whole line can meet (a pattern spanning two commands) never fires when it also carries a `not_` term on `command`, since the two must hold on one Candidate and a `not_` term never reads the whole line. Pipe-to-shell, the usual such pattern, sets `unreadable: command` instead.
- Binding terms to one Candidate reads syntax, not values: `X=-rf; rm $X /` does not meet `starts_with: rm` AND `contains: -rf`.
- A shell call's `path` holds only the files its syntax names. Any unlisted program, an interpreter above all, and `sudo -e` too, writes and reads files handrail never sees, so a positive `path` rule is a denylist aid over shell and a `not_` `path` rule is never an allowlist there. A rule directory guard pairs its `path` rule with a `command` rule for that reason.
- Relative shell targets are not joined to cwd and `cd` is not followed: `cd .handrail/local && cat > a.md` names `a.md`.
- A `path` is cleaned lexically and never resolved against disk, so behind a symlink it names a file other than the one it spells; a symlink already escapes every `path` rule.
- A shell write fills no `content`, `deletes`, `writes_empty` or `removed_content`, so a `deletes` rule misses `rm`; a `command` rule on `rm` covers it.
- A listed reader that also writes is read as a reader: `find .env -delete` and `git -C d checkout -- .env` yield `file_read` payloads only.
- **Network**: `domain` is the host the call names, not where a fetch ends after a redirect the tool follows itself. Internationalized hosts and schemeless URLs are unreadable. On Codex's `webrun`, `click` follows a link the page chose and names no target.
- **Stop**: `stop_hook_active` is set by any Stop hook. If a foreign hook continues the agent first, handrail's block rules on that stop are not evaluated.
- `response` is written by the agent it judges. A rule on it nudges a careless agent and cannot gate a hostile one, which can choose its words. The harm is bounded: a block on `Stop` continues the agent once.
- On Claude Code, a subagent that hands back through `SubagentHandback` leaves only its closing text in `response`. Its report is that tool call's `message`, which no canonical field reads.
- On Codex, a subagent's own compaction fires no start hook, so context injected by `SubagentStart` may not survive it.
- **Harness decisions handrail does not see**: another hook's rewrite (section 4), another PermissionRequest hook's answer to an `ask` (section 4), a model chosen off the wire (section 1), and Codex's sandbox escalation (section 4).
